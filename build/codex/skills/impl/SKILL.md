실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`와 [공통 실행 계약](../../context/runtime-contract.md)과 [작업 시작·재개의 사용자 경험](../../context/start-experience.md), [프로젝트 경험 규칙](../../context/project-experience.md)을 먼저 읽는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


# /impl — 빌드 디스패처 (구현 ⇄ /verify 루프 제어)

## 런타임 기록

명시한 project·slug로 `status`를 확인하고 `transition --action implement`가 성공해야 구현한다. 문서 표식만으로 승인 기록을 대신하지 않는다. 모든 task 명령에 `--project PATH --slug SLUG`를 붙인다. 구현 후 메인이 `transition --action verify --strength light|full`로 라운드를 열고 light는 메인이 직접 `verify-run` 검사·판정을 수행하거나 위임하고 full은 fresh reviewer에게 맡긴다. full 리뷰는 메인이 검산한 뒤 `review`로 등록한다. 판정을 받은 이 디스패처가 통과 시 `transition --action complete`, 구현결함 시 `transition --action implementation-defect`, 설계문제 시 `transition --action design-problem`(요구 변경이면 `requirements-problem`)을 실행한다. 거부·낡은 증거·라운드 상한은 보고하고 완료를 주장하지 않는다. 다음 라운드는 새 독립 검토를 받는다. 구현 루프는 기본 라운드 예산·정체 가드를 유지하며 `--manual-full-continuation`을 전달하지 않는다.

[OS.md](../../OS.md) 개발 흐름의 **③ 구현 단계**를 **조율(제어)하는 한 디스패처**다.
입력은 **승인된 Plan**(`docs/plan/<slug>.md`)과 PRD, 출력은 **실제 코드 + 테스트**다.

> 역할 분리 — **판단은 /verify, 결정은 /impl.** 실제 검증은 /verify 절차를 적용하며 light는 메인이 직접 수행할 수 있다.
> 구현 일꾼(서브에이전트)과 `/verify` 일꾼에게 상황 따라 던지고(dispatch), `/verify`가 낸 **판정대로 분기**한다.
> 검증이 자라도(PR Checks·CI 등) `/verify`에만 들어가므로 이 스킬은 얇게 유지된다.

전달된 인자: `$impl` 뒤의 사용자 메시지.
- 인자가 있으면 → 기능 설명/slug로 사용한다.
- 인자가 없으면 → start에서 전달받은 project·slug·요청·기록과 현재 대화의 문맥을 먼저 재사용한다. 확인할 수 없는 사용자 의도만 질문한다.

## 진행 순서

### [준비] Plan·PRD 확인 + 승인 확인

slug를 정하고 `exec_command`의 `test -f`로 입력을 확인한다.

```
docs/prd/<slug>.md     # 있어야 함
docs/plan/<slug>.md    # 있어야 함 (= 설계 완료)
```

- **Plan이 없으면** → "먼저 `/plan`으로 설계하고 검토 게이트를 통과하세요"라고 안내하고 **멈춘다.**
- **있으면** → Plan·PRD를 `exec_command`로 읽고, **사람이 ② 승인 게이트에서 Plan을 승인했는지** 확인한다.
  명시적 승인("승인", "구현 시작") 없이 임의로 구현에 들어가지 않는다. (OS.md 원칙 1)
- **읽으며 Plan의 내부 모순·현실 불일치**(예: 신규/재활용 상충, 파일명 체계 상충, 제거된 코드 참조)를 점검한다.
  있으면 **정본을 정해 1단계 디스패치 프롬프트에 해소 지침으로 명시**하고, 스스로 못 정할 모순이면 구현 대신 **`/plan`으로 돌려보낸다**(설계문제 분기와 동일).

---

### 승인 Plan의 Task 구성·재개

공통 사용자 경험 카드의 프로젝트 전체 단일 오케스트레이션 절을 위임·기록·재개 규칙 정본으로 적용한다. 메인만 `.tram/local/tasks/<slug>.md`를 갱신하고 사용자 피드백을 작업자에게 전달한다. 기록과 실제 산출물·runtime·작업자 상태를 대조한 뒤 남은 작업을 배정한다. 승인 Plan 본문과 runtime JSON은 진행 목록으로 덮어쓰지 않는다. 필수 검증이 미실행이면 구현 결과와 검증 보류를 구분하며 완료 전이를 실행하지 않는다.

### 1. 구현 디스패치 — ★오케스트레이터 결정★

이 스킬은 오케스트레이터다. **"무엇을 구현할지" 뿐 아니라 "어떻게 디스패치할지"도 매 라운드 결정**한다.
(이게 핵심 — "어떤 일꾼을 어떻게 부를지"는 정적 규칙이 아니라 **이번 일의 모양에 맞춘 결정**이다.)

**1-a. 디스패치 방식 결정** — 이번 라운드 작업의 모양을 보고 고른다:

| 일의 모양 | 디스패치 | 왜 |
|-----------|----------|----|
| **큰 신규·광범위 구현** (여러 파일·새 동작) | **새 구현 에이전트** (adapter의 독립 에이전트 실행, `작업 식별자: implementer`) | 메인 컨텍스트 보호, 병렬·격리 |
| **작고 좁은 보완** (1~2파일·독립적·맥락 적음) | **새 좁은 구현 에이전트**(필요한 것만 담아) | 후속 작업 안 함 |
| **직전 에이전트의 누적 맥락이 정말 필요한 연속 작업** | **같은 에이전트에 adapter의 후속 작업 실행** | 맥락 재구축 비용 > 재로딩 비용일 때만 |

> ⚠️ **후속 작업 비용 주의**: 같은 에이전트에 후속 작업을 보내면 그 에이전트의 **전체 트랜스크립트가 재로딩**될 수 있다.
> 첫 구현으로 거대해진 에이전트를 **작은 보완 때문에 다시 호출하면, 1줄 고치는 데 수십~수백 k 토큰**을 쓸 수 있다.
> **원칙: 후속 작업 재로딩 비용이 변경 크기를 넘으면, 좁은 새 구현 에이전트에 맡긴다.**

**1-b. 결정한 방식으로 디스패치** — 무엇을 넘기든 공통:
- 승인된 Plan의 "구현 단계·손댈 파일·테스트 전략" + PRD 수용 기준,
- **단위/통합 테스트도 함께 작성**(OS.md 원칙 3), 기존 파일을 깨지 말 것.
- **컨텍스트 카드를 프롬프트에 직접 실어 넘긴다(서브에이전트 디스패치 시 필수).** 서브에이전트는 격리
  컨텍스트라 편집 훅의 자동 주입이 안 닿을 수 있다 → 손댈 영역에 해당하는 `<plugin-root>/context/` 카드를
  **`exec_command`로 읽어 그 내용을 디스패치 프롬프트에 함께 넣는다.** `.tram/project.json`에서
  수정 경로에 연결된 프로젝트 카드를 확인한다. 설정이 없으면 조사 작업자에게 대상 프로젝트 규칙 확인을 배정하고
  메인이 미설정을 알린다. 공유 `flow-rules.md`도 전달하며 특정 스택 규칙을 기본으로 적용하지 않는다.
- 작업 메시지는 공통 배정 계약에 따라 "구현" 목적·담당 파일·의존·확정 명령과 반환 근거를 명시한다. 사용자 질문·승인/전이·Task 갱신·재위임을 금지하고 실행 조건 변경 시 중단해 메인에 반환하도록 한다. 재구현(구현결함 분기)이면 **검증자가 짚은 미충족 항목만** 고치게 한다.

### 관련 문서 점검 — 최종 verify 이전

[변경 관련 문서 점검과 보고](../../context/project-experience.md#변경-관련-문서-점검과-보고)를 적용한다. 해당 변경과 관련된 업무규칙·아키텍처·운영 문서만 대조하고 승인 범위 안의 근거 있는 보완을 구현의 일부로 마친다. 관련 문서·근거, 보완 내용 또는 변경 불필요 이유와 미해결 사항을 완료 보고에 포함한다. PRD·Plan 본문은 보존하며 문서 보완 뒤 최종 verify를 실행한다.

### 2. 검증 강도 결정 — ★디스패처 판단★

`/verify`를 부르기 전에, **변경 위험도를 보고 강도를 정한다.**

| 강도 | 언제 |
|------|------|
| **light** (테스트만) | 동작 보존 리팩터링·기계적 변경(import·포매팅·rename)·문서/설정·**잘 덮인** 좁은 버그픽스 — 그리고 영향 영역 테스트가 잘 덮일 때 |
| **full** (테스트+적대적) | 새 기능·동작 변경·보안/인증·외부 입출력 — 또는 커버리지가 약할 때 |

- **애매하면 full**(안전한 쪽).
- "공개 API·시그니처 변경 / 보안·인증 / 성능·동시성 / 외부 입출력·스키마 변경"은 소규모여도 **full**.
- 한 번 full이 필요했던 작업은 보완이 작아져도 종료까지 full을 유지한다. 점수 기준을 피하려고 light로 낮추지 않는다.
- (이번 신규 구현처럼 새 동작이 많으면 full, 동작 보존 리팩터링이면 light.)

### 3. 검증 — `/verify` 호출

메인이 [`/verify`](../verify/SKILL.md)를 읽고 `transition --action verify --strength light|full` 성공 후 검증 시작 `status.snapshot`·`task.round`를 보관한다. 이미 열린 라운드는 실제 상태를 확인해 이어가고 중복 실행하지 않는다. native 실행은 adapter를 따른다.

- light는 메인 또는 구현 담당이 verify 절차의 실제 테스트와 verify-run을 직접 수행할 수 있다. 위임 시 검증 작업자에게 project·slug·강도·현재 라운드·검사 범위를 전달한다.
- full은 메인이 **fresh reviewer를 직접 생성**해 verify의 검토 계약·공유 reviewer 역할·루브릭·최신 대상·프로젝트 카드를 전달한다. 구현자 대화·이전 점수를 물려주지 않는다. 별도 검증 작업자에게 reviewer 생성을 맡기지 않는다.
- 검증 담당은 실제 `verify-run` 검사·판정과 실행 reference를 반환한다. 구현 파일 수정·재위임·Task 갱신·결과 전이는 하지 않는다.

메인은 검사 결과와 full의 5축 합계·0축·min-gate·미충족·축 밖 블로킹을 검산하고 실제 독립 실행 참조와 시작 snapshot/round로 `review`를 등록한다. 새 품질 채점은 하지 않는다. 누락·모순·등록 거부·낡은 증거는 검증 오류로 보고한다. **테스트 실행·기준 대조는 검증 담당의 몫**이며 메인이 결과를 확인해 다음 분기를 결정한다.

---

### 4. 분기 — ★판정대로★ (이 스킬의 핵심 = 결정)

`/verify`의 3갈래 판정에 따라:

- **통과** → 루프 종료(성공). 5로 간다. **full은 리뷰 점수 ≥90 AND 레벨 0인 축 없음**을 검산하고, 테스트/검사 통과·수용 기준 충족·축 밖 블로킹 없음도 확인한다. light는 해당 검사 통과로 종료하며 리뷰 점수를 만들지 않는다.
- **구현결함** → 미달/블로킹 축의 **인용 결함과 수용 기준 미충족·축 밖 지적**만 들고 **1(구현)로 돌아가** 고친 뒤 다시 2~3. 점수 미달이면 부족한 축을 보완한다. 점수만 올리기 위한 요청 밖 구현·중복 테스트는 추가하지 않는다. 메인이 매 라운드 fresh reviewer를 직접 생성해 독립 재채점을 맡긴다.
- **설계문제** → **루프를 탈출**한다. 구현을 더 돌리지 말고, "이건 구현이 아니라 설계 문제"라며
  **`/plan`(또는 `/prd`)으로 에스컬레이션**할 것을 사람에게 보고하고 멈춘다.

**루프 안전장치**
- **최대 `N`회**(기본 5, 최초 구현·검증 포함) 도달 시 멈추고 최종 점수·남은 축/결함과 함께 보고. 자동으로 상한을 늘리지 않는다.
- **진척 없음 감지**: full에서 최초 점수를 기준으로, 이전 최고점보다 높아지지 않은 검증이 2라운드 연속이면 중단한다(동점·하락·오실레이션 포함). 또는 같은 인용 결함이 2회 연속 미해결이면 강도와 무관하게 막힘으로 중단한다. 축 이름이 같다는 이유만으로 서로 다른 결함을 동일한 것으로 취급하지 않는다.
- 매 라운드 한 줄 진행 보고(예: `라운드 2/5 · full · 리뷰 80/100 · 0축 1(테스트 품질) · 축 밖 블로킹 0`). 점수는 10점 단위다. 결과가 누락·모순되면 오류로 멈추며 임의 점수·통과를 만들지 않는다.

---

### 5. 보고 게이트 — ★멈춤★

루프가 끝나면 사람에게 보고하고 **멈춘다.**

```
✅ ③ 구현 완료 (검증 통과) — 라운드 R · 강도 light|full (full: 리뷰 NN/100 · 0축 0 · 축 밖 블로킹 0)
또는  ↩ 설계문제로 에스컬레이션 — /plan 으로 (사유: ...)
또는  ⚠️ 상한/막힘 — 남은 미충족: ...
```

## 수용 기준 (이 스킬이 제대로 동작하는지 검증)

- [ ] Plan이 없거나 승인 전이면 구현에 들어가지 않는다.
- [ ] **디스패치 방식을 일의 크기로 결정**한다(큰 신규=새 에이전트 / 작은 보완=좁은 새 에이전트 / 맥락필요=같은 에이전트 후속 작업). 작은 보완에 큰 에이전트를 다시 호출하지 않는다.
- [ ] **서브에이전트에 디스패치할 땐 손댈 영역의 컨텍스트 카드(`<plugin-root>/context/`)를 프롬프트에 실어** 넘긴다(격리 컨텍스트라 편집 훅 주입이 안 닿으므로).
- [ ] **검증은 `/verify` 절차로 실행**한다(light 직접 수행 허용, full 독립 reviewer 필수).
- [ ] 변경 위험도를 보고 **강도(light/full)를 정해** /verify에 전달한다.
- [ ] `/verify` 판정 **3갈래대로 분기**한다(통과 종료 / 구현결함 재구현 / 설계문제 에스컬레이션).
- [ ] full은 리뷰 ≥90·0축 없음·테스트 통과·기준 충족·축 밖 블로킹 없음일 때만 종료한다. 미달은 인용 결함만 보완하고 fresh reviewer로 재채점하며 light로 낮추지 않는다.
- [ ] 최대 횟수·진척 없음 안전장치로 **무한 루프에 빠지지 않는다.**
- [ ] 끝나면 사람에게 보고하고 멈춘다(자동 커밋·푸시 금지).

## 안전 규칙

- **판단은 /verify, 결정은 /impl.** 검증 로직을 이 스킬에 도로 넣지 않는다(얇게 유지). 디스패치 라우팅도 **결정 테이블**일 뿐 — 무거운 메타-에이전트를 만들지 않는다.
- **에이전트 규모를 변경 크기에 맞춘다.** 작은 보완에 큰 에이전트 후속 작업 금지(전체 트랜스크립트 재로딩 = 낭비). 재로딩 비용이 변경 크기를 넘으면 좁은 새 에이전트.
- **셀프 채점 금지.** 구현 일꾼이 자기 결과를 검증하지 않는다(검증은 /verify).
- **무한 루프 금지.** 최대 횟수·진척 없음 가드 필수. 설계문제는 루프 대신 에스컬레이션.
- **승인 전 구현 금지, 자동 커밋 금지.** 비밀·로컬 DB(.env, *.db)는 커밋 대상 아님.
- 서브에이전트/하위 스킬이 빈 결과·오류를 돌려주면 그대로 알리고 멈춘다.
