실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`와 [공통 실행 계약](../../context/runtime-contract.md)을 먼저 읽는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


## 실행 역할

[단일 오케스트레이션 계약](../../context/start-experience.md)을 따른다. 메인은 이 스킬 전체 흐름을 읽고 직접 수행 또는 단계 배정을 선택하며 작업자는 사용자 질문·승인/전이·Task 갱신·재위임을 하지 않는다. 메인이 도메인·slug를 식별하고 표적 스캔을 작업자에게 배정한다. 작업자는 확증 필요 목록과 근거를 반환하고 메인이 후속 확증 작업자를 직접 배정한다. 메인만 한 번에 한 질문으로 인터뷰하고 교정된 문서·색인·허용된 매핑 작성은 작업자에게 맡긴다.

먼저 [프로젝트 경험 규칙](../../context/project-experience.md)을 읽고 기존 domain 색인·문서·territory 연결을 확인한다. start가 기존 domain 지식을 재사용하는 경우 전체 인터뷰를 반복하지 않지만, 이 스킬을 직접 실행하면 기존 코드 스캔과 사람 검토 게이트를 유지한다. profile territories가 있으면 runtime configure 경로를 우선하고, legacy 프로젝트는 기존 TSV 경로를 따른다.

# /domain — 서비스 도메인 분석 (정체·경계·관계 지식 베이스)

거대한 도메인을 **한 번에** 지도로 그리지 않는다. **서비스 도메인 하나씩** 분석해
`docs/domain/<slug>.md`에 "이게 무엇이고, 무엇과 이어지나"만 적고, 문서끼리 `[[링크]]`로 이어
**탐색 가능한 도메인 지도**를 점진적으로 쌓는다.

> **`/init`과 다르다.** `/init`은 "코드가 **어떻게 생겼나**"(구조·빌드·배치)를 문서화한다.
> `/domain`은 "이 도메인이 **무엇을 의미하고 무엇과 이어지나**"(의미·관계)만 다룬다. **소스 구조는 넣지 않는다.**
>
> **흐름상 위치:** 개발 흐름(③ 구현)의 일부가 아니라 그 앞에 깔리는 **지식 베이스(받침)**다.
> 산출물은 `/prd`(무엇을 만들지)·`/plan`(뭘 재활용할지)이 **더 정확해지도록 먹이는 컨텍스트**다.
>
> **입력은 하이브리드:** 코드로 초안을 뽑고(반증 가능한 신호), 사람 인터뷰로 의미·의도를 교정한다(왜).
> 코드가 없으면 자연히 인터뷰형으로 degrade 한다.

전달된 인자: `$domain` 뒤의 사용자 메시지.
- 있으면 → 분석할 도메인 이름/slug로 쓴다.
- 없으면 → "어떤 서비스 도메인을 분석할까요?"라고 한 줄로 묻고 시작한다.

## 진행 순서

### [준비] slug 확인 + 갱신 모드 판별

메인이 도메인 이름에서 slug를 정하고 조사 작업자가 기존 문서 존재·내용을 확인한다.

```
docs/domain/<slug>.md    # 있으면 = 갱신 모드(기존 내용을 읽고 보강)
```

- 있으면 → `exec_command`로 읽어 기존 내용을 이어 보강한다(통째로 덮지 않는다). 단 **기존 내용도 참고용 초안**이다 — 사람이 갱신을 걸렀으면 낡았을 수 있으니, 코드로 확인되는 항목은 대조해 드리프트를 잡고 그대로 신뢰하지 않는다.
- 없으면 → 신규. 1단계로 간다.

---

### 1. 코드 표적 스캔 — 초안 뽑기 (코드가 있을 때만)

메인이 조사 작업자에게 배정해 `/plan`의 표적 스캔 방식을 재활용한다. **넓게 읽지 말고**, 이 도메인 이름·동의어·키워드로 표적 검색한다.

1. 먼저 **소스 존재 여부**를 값싸게 본다(벤더 제외 — `/skill-stat`·`/plan`과 동일 교훈):
   ```bash
   # exec_command의 workdir를 프로젝트 루트로 지정한다. 훅용 프로젝트 환경변수에 의존하지 않는다.
   ls
   rg -l --hidden -g '!.git/**' -g '!**/.venv/**' -g '!**/node_modules/**' -g '!**/site-packages/**' -g '!**/dist/**' -g '!**/build/**' -i -- "<도메인 키워드>" . | head
   ```
   - **소스가 없으면** → 이 단계를 건너뛰고 **2. 인터뷰로 직행**(인터뷰형 degrade).
2. 소스가 있으면 `exec_command`의 `rg`·`rg --files`로 이 도메인의 **흔적**을 표적 검색한다: 모듈/디렉토리명, 서비스·클래스명, API 경로, 이 도메인을 **언급·호출하는 다른 코드**(= 이웃 도메인 후보).
3. 조사 작업자는 불확실한 관계·미확증 사실(❓)의 **확증 필요 목록과 근거를 메인에 반환**한다. 메인이 항목별 표적 조사 작업자를 직접 배정해 좁게 확증한다. 독립적이고 파일 쓰기가 겹치지 않는 조사만 병렬 실행하며 선행 결과가 필요하거나 실행 한도가 있으면 순차 실행한다. 각 배정에 "도메인 확증: <대상>", "표적 검색 결과만 · 없는 사실 지어내지 마라"를 명시한다.
   - **★세션 컨텍스트도 초안이다★**: 이미 이번 세션에서 그 코드를 보거나 직접 짰더라도(요약 소실·기억 드리프트·merge로 낡음 가능) **기억을 사실로 옮기지 말고** 위 표적 확증에 함께 넣는다. "컨텍스트에 있다 ≠ 지금 코드와 일치".

   - **★모든 docs는 참고용, 코드가 진실★**: `docs/`의 **어떤 문서든** — PRD·Plan·요구사항은 물론 **`docs/domain/`의 기존 도메인 문서까지** — 거기 적힌 도메인 정보를 **사실로 옮기지 마라**. 문서는 코드보다 늦게 갱신돼 **낡았을 수 있고**(리팩터·merge 드리프트), 특히 **사람이 회고/갱신을 거르면 도메인 문서도 그대로 썩는다**. 문서에서 얻은 정체·경계·관계는 **리드(가설)**로만 쓰고, **코드로 확인 가능한 것은 위 표적 확증으로 지금 코드와 대조**한다. 기존 도메인 문서는 [준비] 갱신 모드의 *출발 초안*으로 읽되 그대로 믿지 말고 코드로 드리프트를 잡는다. 코드로 확인 안 되는 왜·의도는 인터뷰로 재확인하거나 ❓로 남긴다.

산출: **코드가 시사하는 초안** — "이 도메인은 대략 이런 일을 하는 것 같고, 무엇과 이어져 보인다"(가설).
**아직 확정이 아니다** — 코드는 *왜*를 말해주지 않는다. 다음 단계에서 사람이 교정한다.

---

### 2. 사람 인터뷰 — 교정·보강 (★메인에서, `/interview` 규율★)

이 단계는 **메인(이 스킬)이 사람과 직접** 한다(서브에이전트에 사용자 인터뷰를 맡기지 않는다).
`/interview`의 규율을 그대로 따른다:

- **한 번에 하나씩** 묻는다(빈 템플릿을 혼자 채우지 않는다).
- **애매하면 AI가 단정하지 말고 되묻는다.**
- 답을 **무비판적으로 긍정하지 않는다** — 중립·냉정하게 압박한다.
- **★적대적 대조★**: 1단계 코드 초안과 사람 답이 **어긋나면 그 불일치를 짚어 확인**한다.
  ("코드에선 X가 이 도메인 안에 있는 것처럼 보이는데, 방금 경계 밖이라 하셨습니다 — 어느 쪽인가요?")

최소 범위(이번 문서에 필요한 것)만 캔다 — 아래 3개면 충분하다. 더 캐지 않는다:
1. **정체**: 이 도메인을 한 줄로 정의하면? 이 도메인의 **책임**(무엇을 담당)?
2. **경계**: 무엇은 이 도메인이 **아닌가**(범위 밖·헷갈리기 쉬운 이웃과의 선)?
3. **관계**: 무엇에 **의존**하나(upstream)? 무엇이 이 도메인에 **의존**하나(downstream)? 어떤 **개념을 공유**하나?

---

### 3. 문서 작성 — `docs/domain/<slug>.md`

메인이 교정된 내용과 근거를 문서 작업자에게 전달하고 작업자가 아래 **최소 템플릿**으로 쓴다. **소스 구조·파일 배치는 넣지 않는다**(그건 `/init`).

```
# 도메인 — <이름>

> 한 줄 정의: <이 도메인이 무엇인지 한 문장>

## 정체 (무엇을 / 책임)
- 담당하는 것: ...
- 핵심 역할: ...

## 경계 (무엇은 아닌가)
- 범위 밖: ... (헷갈리기 쉬운 이웃과의 선 명시)

## 관계 (무엇과 이어지나)
- 의존(upstream, 이 도메인이 기대는 것): [[다른-도메인]] — 왜
- 피의존(downstream, 이 도메인에 기대는 것): [[다른-도메인]] — 왜
- 공유 개념: <이웃과 공유하는 용어/엔티티> ([[링크]])

> 근거: 코드 신호(<파일/심볼, 있으면>) + 인터뷰(사람 확인). 불확실한 항목은 "❓미확인"으로 남긴다.
```

- 관계에 등장하는 다른 도메인은 **`[[slug]]` 링크**로 적는다(아직 문서 없어도 링크로 남긴다 = 다음 작업 표시).
- 코드로도 사람으로도 확정 못 한 건 **지어내지 말고 "❓미확인"**으로 남긴다.

---

### 4. 지도 갱신 — 얇은 색인 (`docs/domain/README.md`)

배정된 문서 작업자가 `docs/domain/README.md`(도메인 지도 색인)에 이 도메인 **한 줄**을 추가/갱신한다(없으면 만든다).
본문은 각 도메인 문서가 단일 출처 — 색인엔 한 줄 요약 + 링크만(원칙 7: 얇은 색인).

```
# 도메인 지도
- [<이름>](<slug>.md) — <한 줄 정의> · 관계: [[이웃1]] [[이웃2]]
```

**목차가 커지면 세분화:** README가 너무 길어지면(대략 도메인 12개 초과·한눈에 안 들어옴) **영역(bounded context)별
하위 목차**로 쪼갠다 — 최상위 README는 *영역 목록 + 각 영역 하위 목차(`docs/domain/<area>/README.md`) 링크*만
남기고, 각 하위 목차가 그 영역의 도메인들을 나열한다. **"색인의 색인"으로 한 단계 더 재귀** — 어느 단계든 얇게
유지(원칙 7). 훅은 최상위 README(라우팅표)만 주입하므로 세분화해도 주입은 얇게 유지된다.

**영역 매핑 갱신 (코드가 있을 때만):** 작업자가 후보 매핑을 작성하고 profile 적용은 메인이 기존 configure 경로로 제어한다. legacy 프로젝트에서만 아래 TSV를 갱신한다.

 `docs/domain/_territory.tsv`에 이 도메인의 **코드 경로 글롭 → slug** 한 줄을
추가/갱신한다(1단계 스캔에서 이미 안다. 예: `app/*⇥auth`). 이 표는 `inject-domain.sh` 훅이 읽어, 그 경로의 코드를
**편집할 때 이 도메인 문서를 자동 주입**하는 데 쓴다. 이미 같은 줄이 있으면 중복 추가하지 않는다.
(경로=구조라 doc **본문**이 아니라 이 **별도 표**에 둔다 — doc 본문은 의미만. 이건 사람 탐색용 지도(README)와 다른, 훅용 배선이다.)

---

### 5. 보고 게이트 — ★멈춤★

작성한 문서 경로와, 관계에서 **새로 등장했지만 아직 문서 없는 이웃 도메인**을 큐로 보고하고 멈춘다.

```
🗺 도메인 분석 완료 — docs/domain/<slug>.md
정체·경계·관계 채움 · 코드신호 <있음/없음> · ❓미확인 N건
다음에 분석할 이웃(문서 없음): [[이웃1]] · [[이웃2]] — /domain <이웃>
```

- 사람이 확인하도록 멈춘다. 이웃 도메인은 **다음 `/domain` 실행**으로 하나씩 이어간다("하나씩" 원칙).

## 수용 기준 (이 스킬이 제대로 동작하는지 검증)

- [ ] **소스 구조를 문서화하지 않는다**(그건 `/init`). 정체·경계·관계만 담는다.
- [ ] 코드가 있으면 **표적 스캔으로 초안**을 뽑고(벤더 디렉토리 제외), 없으면 **인터뷰형으로 degrade**한다.
- [ ] 인터뷰를 **메인에서 한 번에 하나씩**, 무비판 긍정 없이, **코드-사람 불일치를 짚어** 교정한다.
- [ ] 확정 못 한 관계는 **지어내지 않고 "❓미확인"**으로 남긴다.
- [ ] `docs/`의 문서(PRD·Plan·요구사항 **및 기존 도메인 문서**)는 **참고용 리드**로만 쓰고, 코드로 확인 가능한 것은 **지금 코드와 대조**한다(문서 무조건 신뢰 금지).
- [ ] 문서끼리 `[[링크]]`로 잇고, `docs/domain/README.md` 색인을 **얇게** 갱신한다.
- [ ] 코드가 있으면 `docs/domain/_territory.tsv`에 **경로 글롭 → slug**를 중복 없이 유지한다(편집 시 자동 주입의 근거).
- [ ] 목차(README)가 커지면 **영역별 하위 목차로 세분화**한다(색인의 색인, 각 단계 얇게).
- [ ] 보고 게이트에서 멈추고, **문서 없는 이웃 도메인을 다음 작업 큐**로 넘긴다.

## 안전 규칙

- **`/init`과 경계를 지킨다.** 소스 구조·빌드·파일 배치는 이 스킬 밖이다(의미·관계만).
- **하나씩.** 거대한 도메인을 한 번에 다 그리려 하지 않는다 — 도메인당 한 문서, 점진적 지도.
- **없는 관계 지어내지 않기.** 코드로도 사람으로도 확정 못 하면 "❓미확인". 무비판 긍정 금지(`/interview` 규율).
- **모든 docs는 참고용, 코드가 진실.** PRD·Plan·요구사항은 물론 **기존 `docs/domain/` 문서까지** 낡았을 수 있다(사람이 회고/갱신을 거르면 도메인 문서도 썩는다) — 문서 내용은 리드로만 쓰고 **코드로 확인 가능한 것은 지금 코드와 대조**한다. 어느 문서도 무조건 신뢰하지 않는다.
- **얇게.** 최소 범위(정체·경계·관계)를 지킨다. 요청 없이 엔티티·스키마·흐름으로 부풀리지 않는다.
- **모든 산출물은 저장소 안에**(`docs/domain/`). (AGENTS.md 규칙 1)
- 서브에이전트가 빈 결과·오류를 돌려주면 그대로 알리고, 코드 신호가 약하면 인터뷰에 더 기댄다.

## 참고 / 범위 밖

- **`/prd`·`/plan`을 먹이는 컨텍스트.** 도메인이 정리돼 있으면 요구사항·재활용 판단이 정확해진다.
- **자동 주입(훅·계층형).** `_territory.tsv`에 경로가 등록되면 `inject-domain.sh` 훅이 그 코드를 **편집할 때**
  **도메인 목차(README) + 이 문서**(작으면 전체 · 크면 머리+"전체는 직접 읽기(Read)" 포인터)를 세션당 1회 주입한다
  (컨벤션 카드 주입 `inject-context.sh`의 형제). 그래서 문서가 **살아있는 컨텍스트**로 쓰이며(최신성은 위 코드 대조·인터뷰로 확인), 도메인이 커져도 컨텍스트가 폭증하지 않는다.
- **엔티티·데이터 소유·흐름**은 이번 최소 범위 밖이다. 나중에 필요하면 문서에 블록을 더하되, 기본은 얇게 둔다.
