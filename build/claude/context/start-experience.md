# 작업 시작·재개의 사용자 경험

사용자의 작업 의도를 전문 스킬에 전달하고, 현재 근거에 맞는 다음 행동으로 이어간다. 프로젝트 선행 조사·지식 재사용·변경 보호는 [project-experience](./project-experience.md), 실행·승인·검증 계약은 [runtime-contract](./runtime-contract.md), 위험도와 게이트는 [flow-rules](./flow-rules.md)를 따른다.

## 문맥 전달과 질문

start는 대상 project 경로, slug, 사용자 요청·의도, 선택한 route, 시작 또는 재개 여부, 읽은 문서·작업 기록과 runtime 상태를 다음 전문 스킬에 전달한다. `start에서 진입한 흐름`인지도 명시한다. 전문 스킬은 인자가 없어도 이 문맥과 기록을 먼저 읽고 사용한다. 직접 호출에도 대화와 기록에서 대상을 유일하게 확인할 수 있으면 재질문하지 않는다. 사용자 의도나 상충하는 선택 등 확인할 수 없는 정보만 질문하며, 각 전문 스킬의 조사·작성 범위는 유지한다.

명시한 project·slug를 우선한다. 대상이 모호하면 기존 기록과 요청을 대조한다. 재개 후보가 여러 개이고 유일하게 식별되지 않으면 후보·현재 단계·차단 이유를 제시하고 선택 전 실행하지 않는다. 최신 작업을 임의로 선택하지 않는다. 미연결 프로젝트는 기존 init의 확인 절차로 연결한다.

## 준비 상태와 문제 해결 안내

메인은 `python3 "<plugin-root>/runtime/tram.py" doctor --project "<target>"`를 보조 조회해 `readiness`의 요약·문제별 근거·첫 행동과 `runtime`의 실행 패키지 정보를 설명한다. 사용자가 JSON을 해석하거나 진단 명령을 반복 입력하도록 요구하지 않는다. 정상은 관측한 범위에 한정해 한두 문장으로, 문제는 **이유 → 영향 → 먼저 할 행동** 순서로 전달한다. 관측 시점 이후 상태는 바뀔 수 있으므로 쓰기 직전의 기존 검사와 승인 절차를 유지한다.

- `status`: 기존 상태 조회 뒤 진단을 보조 조회한다. 상태 조회가 실패해도 원래 exit/errorCode와 실패 이유를 유지하고 가능한 진단 설명을 덧붙인다. 여러 task 중 하나를 임의로 선택하지 않는다.
- `init`: 기존 연결·설정 결과 뒤 남은 진단 문제를 설명한다. 연결 실패를 숨기거나 진단 결과로 자동 재시도·복구하지 않는다.
- `start`: 기존 전이 검사에서 막혔을 때 관련 진단을 보조 조회한다. 정상 흐름에 필수 진단 게이트를 추가하지 않는다. 승인 부족·낡은 검증 등 작업별 차단과 다음 단계는 기존 `status`가 정본이며, doctor의 정상 판정으로 이를 덮어쓰지 않는다.

살아 있거나 소유권이 불명확한 잠금·실행은 상태 확인을 먼저 안내한다. 손상된 기록은 확인한 오류와 확인 불가를 구별하며, 읽지 못한 상태에서 migration 가능성을 추정하지 않는다. 복수 문제는 `readiness.issues`의 순서를 따라 설명한다. 진단은 읽기 전용이며 자동 migration·복구 적용·잠금 삭제·프로세스 종료를 하지 않는다. 선택 도구 부재를 기본 작업 차단으로 확대하지 않는다.

실행 패키지의 `runtime.version`과 프로젝트 `runtime.project_schema`를 구분한다. `package_identity`·`host_validation`이 unknown이면 각각 패키지 내용 동일성과 실제 호스트 동작을 미확인으로 설명한다. 같은 버전 표시나 진단의 ready만으로 최신 반영·전체 호스트 검증·작업 완료를 주장하지 않는다. 메타데이터가 없거나 진단 자체가 실패하면 확인 가능한 상태와 한계만 보고한다. 조회에서 로그·marker·잠금을 쓰지 않는다.

## 단계와 다음 행동

`status`의 `effective_phase`, `next_action`, `approvals_valid`, `blocked`, `completion_issues`를 함께 읽는다. 아래 표는 full 경로의 안내이며 runtime 출력과 전이 거부를 우선한다. 예외 route는 해당 전문 스킬의 진입 조건과 안전판을 유지한다.

| effective_phase | next_action | 이어갈 역할 |
| --- | --- | --- |
| prd_draft | prd | 기존 재료로 PRD 수집·정제·검토 |
| prd_review | approve-prd | 현재 PRD와 검토 결과 제시, 사람 확정 대기 |
| plan_draft | plan | 유효 PRD 승인 확인 후 기존 코드 조사·설계 |
| plan_review | approve-plan | 현재 Plan 제시, 사람 승인 대기 |
| implementing | impl | 유효 승인 확인·구현 전이 검사 후 Task와 구현 |
| verifying | verify | 현재 코드 기준 실제 검증·판정, impl이 결과 분기 |
| complete | finishing | 유효 완료 근거 보고, 마무리 메모·현재 Git 상태 재관측 및 선택 안내 |

PRD 검토에는 문제·목표·범위·제품 동작과 열린 질문을, Plan 검토에는 구현 접근·변경 파일·위험·검증 방법을 제시한다. 두 사람 게이트는 별개다. 명시적 응답을 원본 대화에서 확인하고 `approve` 저장 성공과 새 status의 승인 유효성·다음 행동을 확인한다. **start에서 진입한 흐름이면 PRD 승인 저장 성공 후 plan 스킬을 읽고 실행하고, Plan 승인 저장 성공 후 impl 스킬을 읽고 실행한다.** 사용자에게 별도 단계 명령을 요구하지 않는다. 직접 prd·plan 호출은 해당 역할까지만 마치고 다음 행동을 안내한다. 저장 실패는 승인이 기록된 것으로 보고하지 않는다.

## 재개와 승인 경계

재개는 읽은 기록과 실제 문서·코드·runtime 근거를 대조해 완료한 일과 남은 일을 구분한다. 유효한 승인을 반복 요청하거나 완료한 일을 이유 없이 다시 수행하지 않는다. 문서 digest 변경·승인 기록 부족·현재 상태와 충돌이면 필요한 승인 검토로 돌아가고 해당 구현을 보류한다. 오래된 검증은 새 검증으로 갱신한다. status 조회 자체는 정합화·전이·승인이나 로그·marker·잠금 쓰기를 하지 않는다. 재개 실행의 정합화는 start와 기존 runtime에 맡긴다.

승인 조건을 지키는 일상 구현 선택·결함 수정·재검증은 계속한다. 목적·범위·제품 동작·보안 정책·외부 계약·비용 조건 변경은 PRD 검토로, 승인한 구현 접근·변경 범위·검증 전략 변경은 Plan 검토로 돌아간다. 기존 승인 문서를 현재 구현에 맞춰 덮어쓰지 않고 [문서 스냅샷 규칙](./doc-conventions.md)의 재작업 절차를 따른다.

## worktree 마무리와 재개

complete/finishing은 구현·검증 완료 뒤의 안내이며 원격 통합 완료가 아니다. 메인이 지정된 프로젝트·slug의 `.tram/local/tasks/<slug>.md` 마무리 구역을 읽고 source/target 경로를 확인한다. 사용자가 worktree 경로를 지정하면 기존 `connect`·`list` 조회로 문맥을 확인하되 자동 연결 저장을 하지 않는다. 경로나 target을 임의 선택하지 않는다.

`python3 "<plugin-root>/scripts/worktree.py" finish-status --project "<source 경로>" [--target "<target 경로>"]`로 현재 상태를 읽는다. 대괄호는 선택 인자 표기이므로 실제 명령에서는 target이 확인된 경우에만 인자를 넣는다. source/target의 branch·HEAD, 미커밋·untracked·ignored 상태와 다음 세 선택의 상태·이유·`next_action`을 함께 보고한다.

| 선택 | 안내와 연결 |
| --- | --- |
| merge | 기존 ancestry·dirty·ignored 충돌·merge preflight의 제한을 보존한다. 가능하면 기존 merge 제안 명령을 안내하며 실제 실행 직전에 재관측한다. |
| PR | 로컬 remote·branch·변경 상태와 도구 가용성만 사전 준비로 설명하고 기존 [push](../skills/push/SKILL.md)·[pr](../skills/pr/SKILL.md)로 연결한다. 인증·원격 접근·실제 PR 성공은 미확인이다. |
| 그대로 두기 | 현재 작업 공간을 보존하고 남은 선택·제한·다음 행동과 재개 경로를 안내한다. 파일 변경·제거를 실행하지 않는다. |

미커밋 변경은 기존 [commit](../skills/commit/SKILL.md) 절차로 연결한다. **선택은 실행 권한이 아니다.** merge·push·PR 생성·worktree 제거는 각 기존 절차의 별도 권한과 확인을 따르며 같은 세션의 유효한 실행 권한은 존중한다. dirty·untracked·ignored 파일을 삭제하거나 변경을 버려 제약을 해소하지 않는다. 제거는 기존 `remove` 보호를 다시 적용하며 강제 제거를 자동 실행하지 않는다. 조회 자체는 설정·runtime·메모·로그를 쓰거나 원격에 접근하지 않는다. 기존 `merge-tree --write-tree` preflight는 Git 객체를 기록할 수 있으나 사용자 파일·refs·HEAD·index를 변경하지 않는다.

메인만 기존 Task 내용을 보존하며 마무리 구역을 추가·보완한다. source/target 경로, 관측 시점의 branch·HEAD, 선택 또는 미결정, 제약·다음 행동, 실행한 스킬·명령의 실제 참조와 완료/미완료를 남긴다. runtime JSON에 마무리 선택 필드나 새 갱신 명령을 만들지 않는다. **status는 로컬 마무리 메모도 쓰지 않는다.**

새 세션의 `start`는 메모가 있어도 현재 경로의 Git 상태와 `finish-status`를 다시 확인한다. 메모는 과거 문맥이며 승인 증거·현재 상태 증거가 아니다. 경로·branch·HEAD 변화는 차이를 표시하고 현재 상태로 안내한다. 사라진 경로를 완료로 간주하지 않는다. 메모가 없으면 현재 관측부터 진행한다. Git 오류·권한 부족·분리된 HEAD 등은 확인 사실과 미확인 항목·이유·다음 행동으로 보고한다.

메모 경로가 ignore되지 않거나 쓰기 권한이 없어 저장할 수 없으면 대화에 저장 제한과 재개에 필요한 프로젝트·slug·source/target 경로·남은 행동을 제공한다. 영속 저장 성공으로 보고하지 않으며 ignore 규칙·권한을 자동 변경하지 않는다.

## 프로젝트 전체 작업의 단일 오케스트레이션

이 절은 전체 18개 스킬과 전문 스킬 직접 호출에 적용하는 역할·배정·기록·재개 계약의 단일 출처다. 경로별 절차·사람 게이트·전문 안전판은 각 `skills/<스킬>/SKILL.md`의 해당 단계가 정본이며, 위임은 그 경계를 바꾸지 않는다.

### 메인과 작업자

- **메인 하나가 사용자 창구다.** 사용자 대화·질문·인터뷰·승인·위험 및 route 판단·배정·결과 통합·예산·중단·최종 보고를 맡는다. 제어용 runtime의 `approve`·`transition`·`configure`·`review`, 짧은 상태 조회, 승인 문서의 상태 저장, Task·진행 기록·증거 등록도 메인이 수행한다.
- **위험과 비용에 따라 직접 수행 또는 위임한다.** 작은 순차 저위험 조사·수정·light 테스트는 메인이 직접 수행할 수 있다. 전문 단계의 작업자 표현은 위임을 선택했을 때의 담당을 뜻한다. 병렬·충돌·고위험 작업은 필요 근거를 남겨 위임한다. 코드·문서 조사, 분석·초안·수정·구현·테스트·측정·도식 생성과 확인, 사용자 요청 및 권한이 확정된 외부 실행을 수행하고 질문 후보·근거·막힘을 메인에 반환한다. 작은 보완은 메인이 직접 수행할 수 있다.
- **메인은 스킬 전체 흐름을 읽고 직접 수행 또는 단계 배정을 선택한다.** 작업자에게 전체 스킬의 오케스트레이터 책임을 넘기지 않는다. 메인만 작업자를 직접 생성·후속 배정하며 작업자는 재위임하지 않는다. 각 배정에 실행 단계, project·slug·요청·route·허용 범위·목표, 소유 파일·의존, 읽을 카드, 확정 명령·권한과 반환 근거를 명시한다. 작업자에게 사용자 질문·승인/전이·Task 갱신·재위임을 금지하고, 승인 조건·대상·HEAD·branch 등 실행 조건이 달라지면 중단해 반환하도록 지시한다.
- **위임과 병렬 실행을 별도로 판단한다.** 순차 실행을 기본으로 하고 파일·포트·DB·출력 디렉터리 등 자원이 독립적인 작업만 병렬 배정한다. 공유 파일 수정 또는 선행 결과가 필요한 작업은 순차 배정하고 환경의 동시 실행 한도를 따른다. 다른 작업자가 있음을 알리고 다른 변경을 되돌리지 않도록 지시한다. 독립적이고 맥락이 적은 보완은 좁은 새 작업자, 이전 맥락이 필요한 연속 작업만 기존 작업자의 후속 작업으로 배정한다.
- **검증은 실제 실행으로 증명한다.** light는 메인 또는 구현 담당이 직접 테스트와 `verify-run`을 수행할 수 있으며 별도 실행 의무가 없다. 위임한 검증 작업자는 검사 중 구현 파일을 수정하지 않는다. full은 메인이 매 라운드 fresh reviewer를 직접 생성하며 reviewer가 실제 `verify-run`과 독립 검사·채점을 수행한다. 메인은 실행 참조와 판정을 검산하고 `review` 등록·결과 전이를 수행한다. 역할 이름만 바꾼 동일 실행을 독립 검증으로 간주하지 않는다.

### Reviewer에게 전달할 의도 근거

사용자 요청을 PRD·Plan 같은 검토 산출물로 구조화했다면, 독립 reviewer에게 산출물과 함께 짧은 provenance block을 전달한다: 원 요청의 압축 요약, 사용자가 확정한 결정과 그 근거, 명시적 가정, 미결정 항목. reviewer는 이를 산출물과 대조해 요약 누락·근거 없는 정책·미결정 누락을 확인한다. 원문 대화 전체나 불필요한 민감정보는 복사·저장하지 않는다. 사용자가 이미 확정한 결정은 새로운 미결정 질문으로 되돌리지 않는다.

### Task 실행 기록과 재개

**메인만 Task 기록을 갱신한다.** full·quick·coverage·perf는 기존 대상 프로젝트 `.tram/local/tasks/<slug>.md`를 사용한다. 승인 Plan이 있으면 목표·승인 PRD/Plan 참조를 연결한다. 승인 Plan이 없는 route에는 요청·route·허용 범위·목표를 기록하고 각 항목의 식별자·수용 기준·담당·실제 실행 참조·소유 파일·의존 관계·진행 상태·완료 근거·제한·다음 행동을 기존 허용 형식으로 유지한다. 배정 전 범위·의존을 기록하고 배정 후 실제 실행 참조를 연결하며 결과 수신 후 파일·검사 명령·결과를 대조해 반영한다. 기존 기록과 부분 진척·실패를 보존하며 체크만으로 완료를 인정하지 않는다.

Task는 실행 목록이며 새 승인 게이트·엔진·스키마가 아니다. 승인 Plan 본문을 진행 목록으로 덮어쓰거나 runtime JSON을 수동 변경하지 않는다. 승인·검증·최종 완료는 기존 runtime이 판정한다. init·interview·domain·retro·diagram·skill-stat 등의 자료 작업은 Task가 없다는 이유로 새 route나 full 시작을 강제하지 않는다. 기존 허용 기록과 대화로 실제 실행 참조·산출물을 반환한다. retro는 새 기록 파일이나 자동 문서 수정을 만들지 않고 skill-stat은 집계를 위한 로그·Task를 만들지 않는다. **status는 메인이 읽기 전용으로 직접 조회하며 작업자 배정·Task·로그·marker·잠금·상태 전이를 발생시키지 않는다.**

재개 전에 runtime·Task·실제 산출물·작업자의 실제 실행 상태를 대조한다. active 또는 중단된 작업자의 종료·상태 확인 전 같은 파일의 작업을 중복 배정하지 않는다. 확인 불가·지원 불가·오류·중단·빈 결과는 메인이 상태·제한·부분 진척을 보고하고 해당 배정·완료를 보류한다. 확인된 독립 작업은 계속할 수 있다. 실제 생성·후속 배정·상태 조회·실행 참조 지원은 adapter와 현재 host 도구 metadata를 확인하며 가짜 실행 참조를 만들지 않는다.

**직접 수행에도 같은 승인·기록·검증 계약을 적용한다.** 작은 순차 저위험 작업에는 별도 명시적 사용자 요청이 필요하지 않다. 필수 역할의 실행 제한은 근거와 함께 보고한다. 필수 독립 검증을 대신하지 않으며 full reviewer를 확보하지 못하면 통과·완료를 보류한다.

## 완료와 제한 안내

같은 세션에서 완료한 작업에 후속 변경을 더했다면, 최종 보고 전에 프로젝트 전체 status를 읽기 전용으로 조회하고 선행 작업의 검증 유효성 변화와 필요한 후속 행동을 함께 설명한다. 여러 작업을 임의로 재개하거나 무관한 작업을 자동 재검증하지 않는다.

결과 보고에는 승인 범위에 대응하는 변경, 실제 실행한 검증과 결과·근거, 미실행 검증과 이유, 남은 위험·제한·다음 행동을 포함한다. 필수 검증을 실행하지 못하면 구현 결과와 검증 보류를 구분하고 검증 완료·전체 완료를 주장하지 않는다. 낡은 증거와 독립 리뷰 부재도 통과로 대체하지 않는다. 기존 라운드 예산·막힘 가드를 유지한다. commit·push·PR은 기존 전문 스킬 계약과 사용자가 부여한 작업 범위·권한을 따른다.
