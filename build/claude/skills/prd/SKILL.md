실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

새 승인 산출물의 읽기 구조는 [문서 규칙](../../context/doc-conventions.md)을, 승인 요약·재승인·문서 안내는 [공통 표시 정책](../../context/start-experience.md#요약문서-안내)을 따른다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`, [공통 실행 계약](../../context/runtime-contract.md), [작업 시작·재개의 사용자 경험](../../context/start-experience.md), [프로젝트 조사·지식 재사용 규칙](../../context/project-experience.md)을 먼저 읽는다. start에서 진입했으면 전달된 조사 요약과 근거를 PRD에 재사용한다. 사용자 자료와 코드로 확인되는 사실을 재질문하지 않고, 결정이 필요한 의도·업무정책·문서와 구현의 충돌만 열린 질문으로 남긴다. 초기 조사를 상세 설계나 파일별 구현안으로 확장하지 않는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


# /prd — 요구사항 수집 → PRD 확정 (① 무엇)

## 런타임 기록

메인이 명시한 project·slug로 `status`를 조회한다. 새 작업이면 `start --route full`을 실행한다. `effective_phase`가 `prd_draft`일 때 작성하며, 이미 `prd_review`면 현재 문서의 검토를 이어간다. 작성·독립 검토 후 사람에게 제출하기 전에 `transition --action submit-prd`를 실행한다. 사람의 확정 응답 뒤 `approve --scope prd --quote TEXT --session REF`를 실행한다. runtime이 최종 상태 표식·digest·승인 기록을 처리하며, 저장 실패면 확정 완료로 보고하지 않는다. 모든 task 명령에 `--project PATH --slug SLUG`를 붙인다. 승인 저장 성공 후 status로 유효성을 확인한다. start에서 진입한 흐름이면 전달 문맥을 유지하여 [plan](../plan/SKILL.md)을 읽고 실행한다. 직접 호출은 ①을 마치고 다음 행동을 안내한다.

[OS.md](../../OS.md) 개발 흐름의 **① 무엇을·왜 단계 전체**를 담당한다. 요구사항을 별도 `docs/requirements/` 파일에 쓴 뒤 PRD로 옮기는 두 산출물 흐름을 없애고, `/prd`가 수집부터 정제·검토·사람 확정까지 책임진다. 유일한 산출물은 `docs/prd/<slug>.md`다.

전달된 인자: `$prd` 뒤의 사용자 메시지.
- 인자가 있으면 기능 설명/slug 및 수집 재료로 쓴다.
- 없으면 start에서 전달받은 project·slug·요청·기록과 현재 대화의 문맥을 먼저 재사용한다. 확인할 수 없는 사용자 의도만 질문한다.

이 스킬은 ① 확정까지 맡는다. start가 수행한 현재 동작의 최소 조사는 전달된 근거로 재사용한다. 추가 재활용 조사와 구현 설계는 ② `/plan`, 구현은 ③ `/impl`의 범위다.

## 진행 순서

### 1. 기능 이름과 수집 재료

영문 kebab-case slug를 정하고 `docs/prd/<slug>.md`만 산출물로 사용한다. 다음 세 갈래 중 맞는 입력을 고른다.

1. **기존 PRD 경로에 문서가 있음:** 파일을 읽는다. `상태: 수집 씨앗`이면 인터뷰 재료로 삼고, 기존 내용을 임의로 버리지 않는다. 구조화된 PRD가 이미 있으면 본문을 수집 재료로 보존해 검토·확정 절차를 이어간다. 수정은 위험·범위에 따라 메인이 직접 하거나 작성자에게 좁게 배정하며, 과거 확정 스냅샷의 재작업은 공통 문서 규칙을 따른다.
2. **사용자가 러프한 설명을 줌:** 대화/인자 내용을 수집 재료로 삼는다. 핵심이 모호하거나 충돌할 때만 필요한 질문을 한다. 이미 충분하면 불필요한 인터뷰를 만들지 않는다.
3. **재료가 거의 없음:** start에서 진입했거나 직접 호출했어도 메인이 같은 대화에서 필요한 의도·동작을 질문하고 같은 PRD 경로에 반영한다. [열린 질문의 능동적 해소](../../context/project-experience.md#열린-질문의-능동적-해소)에 따라 직접 질문 또는 interview 수집 모드를 선택한다. 별도 `/interview` 명령 입력을 요구하지 않는다.

입력이 충분하지 않으면 PRD 내용을 추측해 채우지 않는다. 수집은 “무엇을/왜”까지만 한다.

### 2. PRD 생성

메인은 위험·범위·맥락 재구성 비용에 따라 직접 작성하거나 기존 작성자 역할에 좁게 배정한다. 짧고 순차적인 저위험 요구 정리·작은 보완은 직접 수행할 수 있다. 요구가 길거나 서로 독립된 입력을 대조해야 하거나 독립 작성이 실제 이점이 있으면 adapter로 배정한다. 어느 경로에서도 사용자 의도를 추측하거나 구현 설계로 확장하지 않는다. 작업자에게 맡길 때는 코드를 조사하지 말고 사용자 재료를 구조화하도록 지시한다.

```text
당신은 PRD 작성자다. 코드를 보거나 구현 방법을 제안하지 마라.
아래 수집 재료를 구조화하되, 사용자가 말한 내용을 임의로 바꾸지 말고 모호하거나 비어 있는 점은 열린 질문으로 남겨라.

[수집 재료]
<초안 파일 또는 대화에서 확보한 내용>

아래 Markdown 문서 본문만 반환하라.
# PRD — <기능 이름>
> 상태: 검토 대기 — 사람이 확정하기 전
## 문제 (왜 필요한가)
## 목표 (이 기능이 해결하는 것)
## 사용자 시나리오 (기대 동작)
## 범위 밖 (이번에 안 하는 것)
## 제약 / 조건
## 열린 질문 (사람 확인이 필요한 점)
각 질문 아래에 **답변:** _(여기에 작성)_ 줄을 둔다.
```

위임 응답이 비어 있거나 오류면 그 사실을 알리고 멈춘다. 허용된 `docs/prd/<slug>.md`에 저장하고 산출물·실행 참조를 반환한다. 기존 구조화된 PRD는 불필요하게 다시 쓰지 않고 검토 대상으로 삼되 지적·사용자 답변·수정 요청의 실질 반영은 변경 범위에 맞춰 직접 하거나 좁게 배정한다. 씨앗은 같은 파일에서 정제본으로 진화한다.

### 3. 검토와 사람 게이트

작성·검토에서 발견한 열린 질문은 [공통 질문 정책](../../context/project-experience.md#열린-질문의-능동적-해소)에 따라 메인이 직접 꺼내 해소한다. 문서의 `답변` 칸은 기록용이며 사용자에게 직접 채우라고 요구하지 않는다. 승인에 영향을 주는 미결정을 남긴 채 확정을 요청하지 않는다.

메인이 작성 후 공유 검토자 정의([`reviewer`](../../agents/reviewer.md))를 읽고 따르는 fresh 독립 서브에이전트를 adapter의 독립 에이전트 실행으로 호출한다. 직접 작성한 경우에도 이 검토는 생략하거나 메인 자체 점검으로 대체하지 않는다. 검토 요청에는 수집 재료, 생성 PRD, [의도 출처와 판단 근거](../../context/start-experience.md#reviewer에게-전달할-의도-근거), 그리고 다음 판정 형식을 포함한다.

```text
## 판정: 큰 문제 없음 | 지적 있음
## 짚은 점
- (분류: 누락 | 모순 | 모호 | 오류) 내용 — 근거와 수정 제안
```

의도 출처 block은 최초 요청의 짧은 요약, 사용자가 확정한 결정과 그 근거, 명시적 가정, 미결정 항목만 담는다. 대화 원문 전체나 민감정보를 복사하지 않는다. 검토자는 수집 재료와 PRD를 이 출처에 대조해 요약 누락, 근거 없는 정책, 미결정 누락을 확인한다.

문제·목표·범위·제품 동작·열린 질문을 포함한 PRD 요약과 검토 결과를 사람에게 보고하고 **멈춘다**. 지적 또는 사용자 수정이 있으면 메인이 작성자에게 반영을 배정하고 별도 독립 검토를 다시 배정한다. 사람이 “확정”이라고 하면 메인이 최종 상태 표식을 저장하고 위 `approve` 명령으로 승인 기록을 저장하여 ①을 끝낸다. “Plan 진행”도 확정 의사로 본다. 확정 전에 ②/③으로 넘어가지 않는다.

기존 PRD를 이어 검토하는 경우에도 최신 문서를 읽어 같은 검토·확정 게이트를 적용한다. 열린 질문의 답은 작성자가 문서에 반영하고 메인이 검토를 다시 배정한다. 자료 검토자는 수집 재료·최신 PRD의 읽기 대조 결과만 반환한다. 문서 검토에 구현 검증의 `verify-run`이나 코드 리뷰 JSON을 강제하지 않는다.

## 수용 기준

- [ ] 입력을 기존 씨앗/PRD, 사용자 러프 설명, 재료 없음의 세 갈래로 처리한다.
- [ ] 새 `docs/requirements/` 파일을 만들거나 요구하지 않는다.
- [ ] `docs/prd/<slug>.md`가 유일한 산출물이고, 씨앗은 PRD로 진화한다.
- [ ] 충분한 재료가 없으면 진입 방식과 무관하게 같은 대화에서 직접 질문하거나 interview 수집 모드를 선택한다. 추측으로 요구를 만들지 않는다.
- [ ] 짧고 순차적인 저위험 PRD 작성·보완은 메인이 직접 수행할 수 있고, 독립 이점이 있는 일은 좁게 배정한다.
- [ ] 작성 경로와 무관하게 fresh 독립 reviewer가 원 요청 요약·결정·가정·근거·미결정을 대조한다.
- [ ] 사람의 확정 전에는 상태를 확정으로 바꾸지 않고 Plan/구현으로 넘기지 않는다.

## 안전 규칙

- 사람의 의도·제약·범위를 임의로 바꾸지 않는다. 모호한 점은 열린 질문으로 둔다.
- 수집은 무엇/왜까지다. PRD 작성자에게 코드 조사·구현 설계를 맡기지 않는다. 현재 동작·제약 근거가 부족하면 메인이 별도 조사 작업자에게 좁게 배정해 재사용하고 재활용 조사와 설계는 `/plan`에서 수행한다.
- 모든 산출물은 저장소 안 `docs/prd/`에 둔다.
- 서브에이전트가 빈 결과/오류를 반환하면 그대로 알리고 멈춘다. 직접 수행 경로에는 존재하지 않는 실행 참조를 만들지 않는다.
- 이 스킬은 PRD 문서와 runtime을 통한 작업 기록만 수정한다. 코드 파일을 수정하지 않는다.
