실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`와 [공통 실행 계약](../../context/runtime-contract.md)을 먼저 읽는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


## 실행 역할

[단일 오케스트레이션 계약](../../context/start-experience.md)을 따른다. 메인은 이 스킬 전체 흐름을 읽고 직접 수행 또는 단계 배정을 선택하며 작업자는 사용자 질문·승인/전이·Task 갱신·재위임을 하지 않는다. 작업자가 Git 상태·diff·메시지를 준비하고 메인이 요청 범위·branch·HEAD·기존 staged 변경·민감 정보를 확인한다. 확정한 개별 파일과 메시지의 staging·commit만 작업자에게 배정한다. 실행 직전 HEAD·branch·diff·staged 범위가 달라지면 중단해 반환하며 reset으로 맞추지 않는다.

# /commit — 변경사항 커밋

로컬 변경사항을 의미 있는 단위로 **커밋**하는 스킬입니다. 커밋은 로컬 기록이며, 외부 공개인 푸시는 `$push` 스킬이 담당합니다.

> 설계 원칙: 이름과 동작을 일치시킨다. `$commit`은 기본적으로 **로컬에서 멈춘다.**

전달된 인자: `$commit` 뒤의 사용자 메시지.

- 인자가 있으면 → 커밋 메시지로 사용 (사용자 의도 우선)
- 인자가 없으면 → 변경 내용을 분석해 메시지를 직접 작성
- 푸시가 필요한 요청이면 커밋을 마친 뒤 `$push`로 이어서 처리한다.

## 실행 범위

Codex의 실제 실행 권한은 환경 승인 정책에 따른다. 이 스킬에서는 다음 Git 명령만 사용한다.

- `git status`
- `git diff`
- `git log`
- `git branch`
- `git add`
- `git commit`
- `git rev-parse`
- `git remote`

## 진행 순서

### 1단계: 작업자의 현재 상태·메시지 준비

작업자가 아래 3개 읽기 명령으로 전체 그림을 확인하고 HEAD·branch·staged 목록 및 메시지 초안을 메인에 반환한다. 독립 읽기는 실행 한도 내에서 병렬화할 수 있다.

```bash
git status              # 무엇이 변경/스테이징 되었는가
git diff HEAD           # 실제 변경 내용 (staged + unstaged)
git log --oneline -5    # 기존 커밋 메시지 스타일(언어/형식) 참고
```

확인할 것:

- 커밋할 변경이 있는가? (없으면 "커밋할 변경사항이 없습니다" 알리고 종료)
- 현재 브랜치가 어디인가? (`main`/`master`면 아래 2단계 주의)
- 기존 커밋들이 한국어인가 영어인가, 접두사(`docs:`, `feat:` 등)를 쓰는가

### 2단계: 브랜치 확인 (보호 장치)

메인이 브랜치와 기존 권한을 확인한다. 현재 브랜치가 `main` 또는 `master`이고 사용자가 명시적으로 "main에 커밋해"라고 하지 않았다면, 바로 푸시하지 말고 사용자에게 새 브랜치를 만들지 물어본다. 실수로 보호 브랜치에 푸시하는 것을 방지한다.

> 이 프로젝트는 학습용이라 main 작업이 일반적일 수 있다. 사용자가 main을 쓰고 있던 흐름이면 굳이 막지 말고 가볍게 한 번만 확인한다.

### 3단계: 스테이징

- 의도한 변경만 담는다. 관련 없는 파일이 섞여 있으면 사용자에게 알린다.
- 메인이 기존 staged 변경·민감 정보·사용자 변경을 확인해 확정한 **개별 파일 경로만** 작업자가 스테이징한다. 전체 `git add -A`로 범위를 넓히지 않는다.
- `.gitignore`에 들어가야 할 파일이 스테이징되려 하면 짚어준다.

### 4단계: 커밋

메인이 메시지와 파일 범위를 확정한 뒤 작업자가 staging 결과를 재확인해 커밋한다. HEAD·branch·diff·기존 staged 변경이 준비 때와 달라지면 중단해 반환한다. 위임은 기존 사용자 권한이나 실행 환경 승인을 대신하지 않으며 유효 권한을 다시 묻지 않는다.

- 인자로 메시지를 받았으면 그대로 사용한다.
- 아니면 **변경 내용(diff)을 근거로** 메시지를 작성한다. "왜" 바뀌었는지가 드러나게 한다.
- **기존 커밋 스타일을 따른다** (1단계의 `git log`에서 본 언어·접두사 형식).
- 커밋 메시지 끝에 아래 서명을 붙인다:

```
Co-Authored-By: Codex <noreply@openai.com>
```

### 5단계: 결과 보고

작업자는 실제 커밋 해시·파일·명령 결과를 메인에 반환하고 메인이 사용자에게 보고한다.

- 커밋 해시와 메시지를 보고하고, 원격 푸시가 필요하면 `$push`를 사용하도록 안내한다.

## 안전 규칙

- 커밋은 로컬, 푸시는 외부 반영이다. 이 스킬은 푸시하지 않는다.
- 비밀키·토큰·`.env` 같은 민감 파일이 스테이징에 잡히면 멈추고 알린다.
- 사용자가 보지 못한 변경을 임의로 커밋하지 않는다. 무관한 변경이 섞였으면 먼저 확인한다.
