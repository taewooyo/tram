실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`와 [공통 실행 계약](../../context/runtime-contract.md)을 먼저 읽는다. [프로젝트 경험 규칙](../../context/project-experience.md)도 읽는다. 작은 변경도 관련 문서·코드와 dirty 상태를 먼저 확인하며, 이미 확인된 사실을 다시 묻지 않는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


## 실행 역할

[단일 오케스트레이션 계약](../../context/start-experience.md)을 따른다. 메인은 이 스킬 전체 흐름을 읽고 직접 수행 또는 단계 배정을 선택하며 작업자는 사용자 질문·승인/전이·Task 갱신·재위임을 하지 않는다. 메인이 위험·route·승격과 검증 강도 이력을 판단하고 좁은 스캔·변경·동작 변경 테스트를 작업자에게 단계별 배정한다. light 직접 검증 또는 검증 담당을 선택하고 full이면 fresh reviewer를 메인이 직접 배정하며 판정·3회 제한·중단·완료를 통합한다.

# /quick — 가벼운 트랙 (작고 저위험한 변경)

현재 연결된 프로젝트에서 범위가 작고 저위험한 변경을 바로 요청할 때 사용한다. 새 작업의 요구사항 정리·재개는 `start`, 프로젝트 연결은 `init`이다. 현재 작업공간이 기본이며 분리가 필요하면 새 작업 진입인 `start`에서 선택형 worktree를 고른다.

## 런타임 기록

메인이 상태 조회·route·검증 강도·라운드와 `transition`·승인/증거 등록을 제어한다. 작업자는 배정된 소유 파일의 변경·검사·측정과 실제 `verify-run`만 수행하고 결과·실행 참조를 메인에 반환한다.

위험 감별을 통과하면 `start --route quick`으로 작업을 만들거나 `status`로 기존 작업을 재개한다. `transition --action implement` 후 변경하고 verify 스킬에 최초 기본 light 검증을 맡기되, full 이력이 있으면 기록된 full 강도를 유지한다. verify는 `transition --action verify --strength light|full`·`verify-run --command ID`로 증거를 남긴다. 이 스킬이 판정에 따라 `transition --action complete` 또는 `implementation-defect`를 실행한다. 위험·범위가 커지면 `transition --action escalate`로 full의 PRD 단계로 승격한다. 모든 task 명령에 `--project PATH --slug SLUG`를 붙인다. runtime 거부를 수동 상태 수정으로 우회하지 않는다.

[OS.md](../../OS.md) 개발 흐름의 **가벼운 옆길**이다. 풀 흐름(요구사항→PRD→Plan→구현)은
**큰 기능**용이라, 작은 변경에까지 강제하면 배보다 배꼽이다. 이 스킬은 그 과함을 덜어낸다.

> 설계 원칙: **세리머니는 위험도에 맞춘다.** 이 OS는 이미 뒤쪽(`/impl`)에서 검증을 `light/full`로
> 나눈다 — `/quick`은 그 "위험도 스케일링"을 **흐름 앞쪽까지** 넓힌 것이다. 새 발명이 아니라 확장.

전달된 인자: `$quick` 뒤의 사용자 메시지.
- 있으면 → **변경 설명**으로 쓴다.
- 없으면 → "무엇을 가볍게 바꿀까요?"라고 한 줄로 묻고 시작한다.

## 이 트랙에 들어오는 것 / 아닌 것

- ✅ **들어옴**: 버그·QA 수정, 작은 정책/스펙 변경, 문구·설정·문서 손질, 좁은 보완. **기준 = 종류가 아니라 "작고 저위험".**
- ❌ **아님(→ `/start`)**: 새 기능, 고위험(보안·인증·과금·마이그레이션), 설계 판단이 필요한 것, 여러 영역에 걸친 큰 변경.

> 판단이 서면 바로 하고, 애매하면 **한 급 위로** 본다(안전한 쪽). 하다 커지면 승격한다(아래 5).

## 진행 순서

### 1. 빠른 이해 — 재활용 먼저 (묻기 전에 훑기)

메인이 배정한 조사 작업자가 `rg`·파일 읽기로 **관련 코드·문서만** 좁게 훑고 재활용·위험 근거를 반환한다. 새로 짜기 전에 **기존 것 재활용**을 먼저 본다.

> 이 스캔은 **두 역할**을 한다: ① 재활용거리 찾기, ② **이게 `/quick` 감이 맞는지 감지.**
> 훑다가 "손댈 데가 넓다 / 얽혀 있다 / 설계가 필요하다" 싶으면 — 그게 곧 **2의 승격 신호**다.
> `/plan`과 다른 건 '재활용을 보느냐'가 아니라 **깊이**다: `/plan`은 갭을 **병렬 조사·문서화·게이트**,
> `/quick`은 **메인이 직접 좁게 조사하거나 작업자에게 배정**한다. 같은 원칙(재활용 우선)을 위험도에 맞춰 가볍게 할 뿐, 깊은 조사는 `/plan` 몫.

### 2. 위험 감별 — ★값싸게, 그러나 반드시★

메인이 스캔 결과를 대조해 바꾸기 전에 **저위험이 맞는지** 판단한다. 아래 중 하나라도 걸리면 **`/quick` 감이 아니다:**

- 공개 API·시그니처 변경 / **보안·인증·권한** / 과금·결제 / 데이터 마이그레이션·스키마 변경
- 여러 영역에 파급 / 되돌리기 어려움 / "이거 어떻게 할지 설계가 필요한데?" 싶음

→ 걸리면 **멈추고** "이건 가벼운 트랙 범위 밖입니다. `/plan`(또는 `/start`)로 가는 걸 권합니다"라고
보고한다. **억지로 `/quick`으로 밀지 않는다.**

### 3. 변경 수행 — 작업자에게 좁게 배정

메인이 허용 파일·목표·완료 조건을 좁게 배정하고 작업자가 변경한다. 관련 없는 것에 손대지 않으며 변경 근거·diff·막힘을 메인에 반환한다.

### 4. 테스트 — 동작이 바뀌면 나란히 (비협상)

- 작업자는 **동작(behavior)이 바뀌면 테스트를 함께** 넣거나 갱신한다. (OS 공통규칙 — 테스트 없는 동작 변경 = 미완료)
- 순수 문구·주석·포매팅처럼 동작이 안 바뀌면 테스트는 생략 가능.
- 비협상 규칙의 단일 출처는 [`<plugin-root>/context/flow-rules.md`](../../context/flow-rules.md) — 테스트·재활용·안전은 여기서 산다.

### 관련 문서 점검 — 최종 verify 이전

[변경 관련 문서 점검과 보고](../../context/project-experience.md#변경-관련-문서-점검과-보고)를 적용한다. 해당 변경과 관련된 업무규칙·아키텍처·운영 문서만 대조하고 승인 범위 안의 근거 있는 보완을 구현의 일부로 마친다. 관련 문서·근거, 보완 내용 또는 변경 불필요 이유와 미해결 사항을 완료 보고에 포함한다. PRD·Plan 본문은 보존하며 문서 보완 뒤 최종 verify를 실행한다.

### 5. 검증 — `/verify` 호출 (최초 기본 light, full 이력 유지)

메인이 [`/verify`](../verify/SKILL.md) 흐름을 읽고 검증 실행을 직접 배정한다. 최초 기본 강도는 `light`다. 먼저 `status`의 `task.verification_strength`·`task.full_required`를 확인하고, 과거 full 검증 또는 full 필요 판정이 있으면 재시도도 **full을 유지**한다. 위험·약한 커버리지 때문에 full로 높인 이력을 초기화하거나 light로 낮추지 않는다. native 호출 방식은 adapter를 따른다. 자체 검증을 새로 만들지 않는다(재활용).
`/verify`의 판정대로:

- **통과** → 6으로.
- **구현결함** → 짚인 것만 고쳐 **3~5 재시도**(작은 루프, 최대 3회 · 진척 없으면 멈춤).
- **설계문제** → **루프 탈출.** "이건 구현이 아니라 설계 문제"라며 **`/plan`으로 승격**을 보고하고 멈춘다.

> 위험이 애매하거나 커버리지가 약하면 이 트랙이 아닐 수 있다 → 2로 돌아가 승격을 고려한다.

### 6. 보고 게이트 — ★멈춤★

```
✅ 가벼운 변경 완료 (/verify light|full 실제 강도 통과) — <한 줄 요약>
또는  ↩ 범위 밖/설계문제 — /plan·/start 로 승격 (사유: ...)

[변경] 수정 파일 · 테스트 N/M (동작 변경 시)
[관련 문서] 확인한 문서·근거 · 보완 내용 또는 변경 불필요 이유 · 조사 한계/미해결 사항
다음은 ④ 마무리입니다. 확인 후 /commit 으로 진행하세요.
```

코드를 만졌으니 사람이 확인하도록 멈춘다. **임의로 커밋·푸시하지 않는다(④의 몫).**

## 수용 기준 (이 스킬이 제대로 동작하는지 검증)

- [ ] 요구사항·PRD·Plan 문서를 **만들지 않는다**(가벼운 트랙).
- [ ] 변경 전 **위험 감별**을 하고, 고위험·설계필요면 **멈추고 승격을 권한다**(억지로 안 밀어붙임).
- [ ] 새로 짜기 전 **기존 코드 재활용**을 먼저 본다.
- [ ] **동작이 바뀌면 테스트**를 함께 넣는다(비협상). 안 바뀌면 생략 가능.
- [ ] 검증은 자체 절차를 만들지 않고 `/verify`를 로드·실행한다(최초 기본 light, full 이력은 재시도에서도 유지).
- [ ] 설계문제 판정이면 루프 대신 **`/plan` 승격**으로 보고한다.
- [ ] 끝나면 보고하고 멈춘다(자동 커밋·푸시 금지).

## 안전 규칙

- **범위를 지킨다.** 고위험·새기능·설계필요는 `/quick`이 아니다. 애매하면 한 급 위로(안전한 쪽).
- **가볍다 ≠ 안전 생략.** 동작 변경엔 테스트, 위험·되돌리기 어려운 건 사람 확인 — 이건 못 줄인다.
- **재활용 우선.** 검증(`/verify`)·규칙(`flow-rules.md`)을 새로 만들지 말고 재사용한다.
- **자동 커밋 금지.** 비밀·로컬 DB(.env, *.db)는 커밋 대상 아님. 마무리는 `/commit`.
- 하위 스킬(`/verify`)이 빈 결과·오류를 돌려주면 그대로 알리고 멈춘다.
