현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`, [공통 실행 계약](../../context/runtime-contract.md), [단일 오케스트레이션 계약](../../context/start-experience.md), [프로젝트 경험](../../context/project-experience.md)을 먼저 읽는다. start에서 수행한 조사와 문서·코드로 확인 가능한 사실을 재사용하고, 사용자 의도·업무정책처럼 사용자 판단이 필요한 내용만 질문한다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


# /interview — 요구사항 인터뷰 (① 무엇, /prd의 수집 도구)

[OS.md](../../OS.md) 개발 흐름의 **① 무엇 단계**에서 수집을 맡는 도구다.
`/prd`가 요구하는 수집 재료를 **혼자 빈 페이지로 채우는 대신, 질문으로 캐내** `docs/prd/<slug>.md`의 씨앗으로 저장한다. (배경·원칙은 OS.md를 따른다.)

```
[/interview] 질문 루프 ──▶ docs/prd/<slug>.md (수집 씨앗)
                                  │
[/prd] 씨앗 읽음 ──▶ PRD 정제 ──▶ reviewer 검토 게이트 ──▶ 사람 확정
```

**이 스킬의 범위 = PRD 수집 씨앗을 저장하는 것까지.** PRD 정제·적대적 검토·확정은 `/prd`가 한다.
메인이 질문의 의존 관계에 맞춰 인터뷰와 저장 의사 확인을 진행한다. 작업자는 기존 자료의 질문 후보·근거 조사와 저장 요청 후 허용된 씨앗 작성만 맡는다. PRD 정제·독립 검토를 여기서 강제하지 않는다.

전달된 인자: `$interview` 뒤의 사용자 메시지.
- 있으면 → 개발할 **기능 설명**(slug 추정·첫 질문 맥락)으로 쓴다.
- 없으면 → "어떤 기능의 요구사항을 인터뷰할까요?"라고 한 줄로 묻고 시작한다.

## 호출 흐름 안의 수집 모드

start·prd가 [공통 질문 정책](../../context/project-experience.md#열린-질문의-능동적-해소)에 따라 선택한 경우 기존 project·slug·확인한 답을 재사용한다. 아래 질문·종료 기준을 적용하되 별도 씨앗을 만들거나 저장 확인 게이트를 추가하지 않는다. 수집한 답과 남은 질문을 호출한 start·prd에 반환하여 현재 미승인 PRD와 기존 검토·사람 승인 흐름으로 이어간다. 이미 존재하는 PRD를 씨앗으로 덮어쓰지 않는다. 아래 씨앗 저장·인계 절차와 직접 호출의 중단 경계는 독립 interview 호출에 적용한다.

## 이 스킬의 태도 (매 질문에 적용하는 규칙)

1. **애매하면 판단하지 말고 물어본다.** AI가 빈칸을 추측으로 메우지 않는다. 정보가 없으면 질문한다.
2. **무비판적 긍정 금지 — 중립·냉정하게.** 사람이 준 답을 그대로 받아 적지 않는다. 모호·모순·근거
   없는 희망사항이면 **되물어 압박한다.** 판단할 땐 근거·객관 신호를 같이 댄다("그건 어떻게
   측정해요?", "그거 이번 범위 맞아요? 배경(2번칸)과 안 맞아 보여요").
3. **답에 맞춰 질문한다.** 앞 답에 의존하는 질문은 순서대로, 독립적인 질문은 소수로 묶는다. 고정 질문 수를 강제하지 않는다.
4. **꼬리 질문.** 결정에 필요한 내용이 모호하거나 충돌하면 구체화한다("예를 들면?", "그때 사용자는 뭘 기대해요?").
5. **이미 아는 건 안 묻는다.** 자료로 확인한 사실과 사용자가 확정한 답은 재사용한다. 추정과 정책 충돌만 확인한다.
6. **못 물어보고 가정해야 하면 가정을 명시한다.** "가정: ~ (아니면 알려주세요)"로 드러내 확인받는다.
7. **실현 가능성 감별(되는 얘긴지) — 값싸게만.** 요구가 이번 스택·제약에서 현실적으로 구현 가능한지
   감을 잡는다. 명백히 불가능·모순이거나(예: "인증 없음"인데 "내 것만 보기") 스택 대비 과하면(실시간·대규모)
   **긍정 말고 되묻는다**(규칙 2의 연장). 단 **깊은 기술 조사는 하지 않는다** — "어떻게"는 `/plan` 몫이다.
   여기서는 "될 법한가·이번 범위가 맞나"까지. 못 푸는 우려는 md에 남긴다: 확정 불가→**5.범위 밖**,
   조건부 가능→**4.제약**, 판단에 기술 조사가 필요→그대로 두고 "확인 필요"로 표시해 `/prd`·`/plan`에 넘긴다.
8. **묻되 선택지·추천을 얹는다 — 빈칸보다 대안.** 특히 꼬리질문(규칙 4)에서 그냥 열린 빈칸으로
   던지지 말고, **구체적 대안 2~3개를 제시하고 그중 내가 추천하는 것을 근거와 함께** 짚는다.
   예: *"저장을 A) 로컬 JSON 파일 (간단·이번 스택에 자연스러움 — 추천) / B) SQLite (유연하지만 이 범위엔 과함) /
   C) 인메모리 (데모용, 영속성 없음) 중 뭘로 볼까요? — 이 중 없거나 다르면 알려주세요."*
   목적은 사람이 **고르거나 반박하기 쉽게** 하고 트레이드오프를 눈에 보이게 만드는 것이다.
   단, 이건 규칙 1·2와 **충돌하지 않는다** — **추천 ≠ 넘겨짚기**(빈칸을 몰래 메우는 게 아니라 근거를 대고
   제안하는 것이다), **추천 ≠ 무비판 긍정**(사람이 고른 뒤에도 모호·모순이면 계속 압박한다). 지킬 것:
   - 대안은 **진짜 선택지**여야 한다. 정답 하나 정해두고 들러리를 세우지 않는다. 늘 **"이 중 없음/다름"의 탈출구**를 연다.
   - 추천에는 **근거와 함께 트레이드오프·위험**을 붙여 반박거리를 준다. 의미가 명확한 동의는 받아들이고 모호함·충돌만 되묻는다.
   - 실현가능성(규칙 7)이 걸리는 안은 이유와 함께 빼거나 "이건 이번 스택엔 무리"라고 표시해, 되는 안 위주로 제시한다.

> 왜 이런 태도인가: 요구사항 단계의 실패는 대부분 "AI가 좋게 넘겨짚어서" 생긴다.
> 인터뷰는 그 넘겨짚기를 **질문으로 되돌리는** 장치다. 내용의 주인은 끝까지 사람이다.

## 자기합리화 차단 — "이 생각이 들면, 그게 넘겨짚기 알람이다"

위 태도(특히 규칙 1·2)는 실전에서 아래 변명들 때문에 무너진다. **이런 생각이 스치는 순간이
곧 "지금 넘겨짚고 있다"는 신호다.** 생각대로 행동하지 말고 멈춰서 반대로 한다.

| 드는 생각 | 실체 (무슨 규칙을 어기는가) | 대신 한다 |
|-----------|------------------------------|-----------|
| "사람 의도가 뻔하지" | 규칙 1 회피 (추측으로 메움) | 근거가 있는 답은 재사용하고 미결정 의도만 묻는다. |
| "표준적으로 보통 이렇지" | 일반론으로 이 사람의 답을 대체 | 일반론 말고 **이 사람·이 프로젝트**에게 묻는다. |
| "좋은 답이네, 넘어가자" | 규칙 2 회피 (무비판 긍정) | 모호·모순·근거 없으면 **되묻는다.** |
| "더 캐면 귀찮아하겠지" | 꼬리질문(규칙 4) 회피 | 결정에 필요한 미결정만 질문한다. |
| "요구사항이니 일단 받아적자" | 실현가능성(규칙 7) 회피 | "이번 스택·제약에서 되는 얘기 맞아요?" |
| "빨리 6칸 채우게 몰아서 묻자" | 규칙 3 회피 (질문 폭탄) | 의존 질문은 순서대로, 독립 질문은 소수로 묶는다. |
| "완벽히 다 채워야 끝이지" | 종료조건 회피 (무한 심문) | 빈칸 허용. 못 푼 건 /prd 가 이어받는다. |
| "추천안 하나 던지고 동의받으면 끝" | 규칙 2·8 회피 (선택지로 마무리 압박) | 선택의 의미가 명확하면 동의를 반영하고 모호한 지점만 묻는다. |
| "괜히 대안 주면 유도하는 거 아냐" | 규칙 8 회피 (빈칸으로 되돌아감) | 진짜 선택지 + 탈출구면 유도가 아니라 **답하기 쉽게** 하는 것. |

> 핵심: 확인된 사실과 미결정을 구분한다. 불필요한 확인은 줄이되 중요한 결정을 추측하지 않는다.

## 진행 순서

### [준비] 기능 이름(slug) 정하기

기능 설명에서 짧은 파일명용 slug를 정한다(영문 kebab-case 권장).
예: "다크모드 토글" → `dark-mode-toggle`. 산출물 경로:

```
docs/prd/<slug>.md   # 이 스킬의 출력 = 수집 씨앗, /prd가 정제
```

저장 요청 전에는 디렉토리나 씨앗 문서를 만들지 않는다. 저장 요청 후 작성 작업자가 필요한 디렉토리를 프로젝트 안에 생성한다.

### [0] 이미 아는 것 흡수 — ★묻기 전에 먼저★

자료 작업자의 근거와 질문 후보를 받아 메인이 **이미 답이 있는 칸을 걸러낸다**(규칙 5). 코드까지 파고들지는 않는다
— 이 단계는 "무엇을/왜"이지 "어떻게"가 아니다(구현 조사는 /plan 몫).

- 자료 작업자가 `exec_command`의 `test -f`로 `docs/prd/<slug>.md` 존재와 기존 내용의 근거를 확인해 메인에 반환한다.
  - **수집 씨앗이 있으면** → 읽어 이미 채워진 칸은 묻지 않고 빈·모호한 칸만 다룬다. 기존 내용을 보존한다.
  - **상태가 수집 씨앗이 아닌 PRD면** → 확정 PRD를 씨앗으로 덮지 않는다. `/prd`에서 수정·검토를 이어가도록 안내하고 멈춘다.
- 인자로 준 기능 설명, 있으면 `README.md`·`AGENTS.md` 정도만 훑어 **유추 가능한 것**을 뽑는다.
  → 자료로 확인한 사실은 재사용하고 유추만 가능한 정책은 질문한다.

### [1] 인터뷰 루프 — 6칸을 채운다

목표는 **/prd가 정제할 수집 재료의 6칸**을 채우는 것이다. 이 6칸이 곧 인터뷰의 지도이자 종료 조건이다.

| # | 칸 | 캐는 것 |
|---|----|--------|
| 1 | 한 줄 요약 | 이 기능을 한 문장으로 |
| 2 | 배경 / 문제 | 왜 필요한가, 지금 뭐가 불편한가 |
| 3 | 원하는 동작 | 사용자가 뭘 할 수 있어야 하나 (시나리오) |
| 4 | 제약 / 조건 | 꼭 지킬 것 (성능·호환·마감 등) |
| 5 | 이번에 안 할 것 (범위 밖) | 혼동 막으려 명시적으로 제외 |
| 6 | 참고 | 관련 링크·기존 기능·예시 |

진행 방식:
- 대체로 2 → 3 → 1 → 4 → 5 → 6 순이 자연스럽다(왜→무엇→요약→제약→경계→참고).
  하지만 **앞 답에 따라 유연하게** 바꾼다. 규칙 1~6을 매 질문에 적용한다.
- 답이 모호하면 그 칸을 **닫힌 걸로 치지 않는다.** 압박(규칙 2)·꼬리질문(규칙 4)으로 또렷해질 때까지.
- 사람이 부담 갖지 않도록 가끔 진행 상황을 가볍게 알린다("6칸 중 4칸 찼어요, 두 개만 더").

### [2] 종료 조건 — 무한 심문 금지

아래 중 하나면 인터뷰를 멈춘다:
- 6칸이 **"PRD를 만들 만큼" 찼다.** (완벽할 필요 없음 — 빈칸은 남겨도 된다. /prd 가 "열린 질문"으로 이어받는다.)
- 사람이 "그만", "이 정도면 됐어"라고 한다.

> 모든 칸을 억지로 다 채우려 하지 않는다. 모르는 건 비워 두고 /prd 로 넘기는 게 정상이다(규칙 1의 연장).

### [3] 요약·확인 — ★게이트(사람이 내용의 주인)★

저장 전에, 캐낸 내용을 **6칸 형식으로 요약**해 보여주고 확인받는다. 여기서 사람이 고칠 수 있다.

```
📋 인터뷰 정리 (아직 저장 전) — <기능 이름>

1. 한 줄 요약: ...
2. 배경 / 문제: ...
3. 원하는 동작: ...
4. 제약 / 조건: ...
5. 이번에 안 할 것: ...
6. 참고: ...
(비운 칸: 없음 / 있으면 "N번칸은 비워둡니다 — /prd 에서 열린 질문으로 남겨요")

이대로 docs/prd/<slug>.md 에 수집 씨앗으로 저장할까요?
고칠 게 있으면 알려주세요. "저장" 하면 파일로 남깁니다.
```

### [4] 저장 & 인계

사람이 "저장" 신호를 주면 메인이 확인된 요약을 작성 작업자에게 전달한다. 작업자는 아래 형식(수집용 6칸)으로
`docs/prd/<slug>.md`에 허용된 편집 도구로 작성하고 산출물·실행 참조를 반환한다. 이미 있던 씨앗이면 사람이 쓴 부분을 보존하며 수정한다.

```markdown
# 수집 원재료 (인터뷰) — <기능 이름>

> 상태: 수집 씨앗 — /prd 정제·검토·확정 대기
> 이 인터뷰 내용은 PRD가 아닙니다. /prd가 이를 읽어 정제 PRD로 바꿉니다.

## 한 줄 요약
...

## 배경 / 문제
...

## 원하는 동작
...

## 제약 / 조건
...

## 이번에 안 할 것 (범위 밖)
...

## 참고
...
```

저장했으면 다음으로 넘긴다 — **단, 임의로 /prd 를 실행하지 않는다.**

```
✅ 수집 씨앗 저장 완료 → docs/prd/<slug>.md
다음은 ① PRD 정제·검토입니다. "/prd" 라고 하시면 이 씨앗으로 이어갑니다.
```

## 수용 기준 (이 스킬이 제대로 동작하는지 검증)

- [ ] `/interview "샘플"` 실행 시 질문 의존성에 맞춰 필요한 6칸의 내용을 수집한다(질문 폭탄 X).
- [ ] 답이 모호·모순이면 그냥 받아 적지 않고 **되물어 압박**한다(중립·냉정).
- [ ] 꼬리질문 시 빈칸만 던지지 않고 **구체적 대안 2~3개 + 추천(근거)**를 얹되, "이 중 없음/다름" 탈출구를 열고 유도하지 않는다(규칙 8). 의미가 명확한 동의는 재확인하지 않는다.
- [ ] "사람 의도 뻔하지" 류의 합리화가 떠올라도 확인된 사실과 미결정을 구분한다(자기합리화 차단).
- [ ] 자료로 확인한 사실과 확정한 답은 재사용하며 미결정 정책은 질문한다.
- [ ] 이미 있는 `docs/prd/<slug>.md` 수집 씨앗은 덮어쓰지 않고 **빈 칸만** 인터뷰한다.
- [ ] 6칸이 차거나 사람이 그만하면 멈춘다(**무한 심문 X**). 빈칸은 남겨도 된다.
- [ ] 명백히 불가능·모순이거나 스택 대비 과한 요구는 **실현가능성으로 되묻고**, 못 풀면 범위밖/제약/"확인 필요"로 남긴다(깊은 기술 조사는 안 한다 — 그건 /plan).
- [ ] 저장 전에 **요약·확인 게이트**에서 멈추고, "저장" 신호에만 파일로 쓴다.
- [ ] 산출물은 **docs/prd/<slug>.md의 수집 씨앗**이며 `/prd`가 정제 PRD로 바꾼다. 별도 requirements 파일을 만들지 않는다.
- [ ] **임의로 /prd·Plan·구현으로 넘어가지 않는다.**

## 안전 규칙

- **추측으로 채우지 않는다.** 모르면 묻는다(규칙 1). 못 물어 가정하면 가정을 드러낸다(규칙 6).
- **사람이 쓴 내용을 임의로 바꾸지 않는다.** 이미 채워진 칸은 존중하고, 빈·모호한 것만 다룬다.
- **문서만 만든다.** 코드 파일을 수정하지 않는다(요구사항 단계는 "무엇을/왜"까지).
- **게이트를 넘지 않는다.** 요약 확인 전에 저장하지 않고, 저장 후 임의로 /prd 를 실행하지 않는다.
- **모든 산출물은 저장소 안에** 둔다(`docs/prd/`). (AGENTS.md 규칙 1)
