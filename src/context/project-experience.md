# 프로젝트 조사·지식 재사용·작업 공간 경험

이 카드는 전체 스킬이 공유하는 프로젝트 조사·지식·작업 보호 규칙의 단일 출처다. 사용자에게 필요한 결정은 남기되 확인 가능한 사실은 먼저 찾는다. 작은 순차 저위험 조사는 메인이 직접 수행할 수 있고 위임 시 실질 조사·문서 작성은 작업자가 수행하며 메인이 대상 식별·조사 배정·결과 통합·질문·지식 반영 범위 판단을 맡는다. 배정·기록·재개는 [단일 오케스트레이션 계약](./start-experience.md)을 따른다.

## 질문 전 조사

1. 메인이 요청과 대화에서 대상 프로젝트·작업·요청 범위를 먼저 식별한다. 식별할 수 없는 값만 간단히 질문한다.
2. 배정된 작업자가 코드 편집 전 [project-context](../scripts/project-context.py)의 `workspace`로 현재 브랜치·HEAD·dirty 상태를 확인한다. 맡을 경로를 알면 `--path`를 전달하고, 연관된 변경을 자세히 봐야 할 때만 `--all`을 사용한다.
3. 작업자가 같은 도구의 `knowledge`로 코드 경로에 연결된 domain 문서 후보를 찾는다. 작업과 직접 관련된 후보와 프로젝트의 기존 업무규칙·아키텍처·운영 지침을 읽는다. 자동 주입에만 기대지 않는다. `init`이 이미 찾아둔 검증 명령과 컨벤션도 관련되는 만큼 참조한다.
4. 작업자가 요청에 필요한 최소 범위의 코드·테스트를 읽어 현재 동작과 제약을 확인한다. 검색 결과·근거 경로·질문 후보를 메인에 반환하고 메인은 허용된 진행 기록에 반영한다. 조사 사실, 사용자가 승인한 결정, 미확인 가설을 구분한다.

코드가 보여주는 동작은 그 자체로 승인된 의도나 업무정책을 증명하지 않는다. 문서·테스트·코드가 어긋나면 각각이 보여주는 근거와 충돌을 보고한다. 메인은 사용자 결정이 필요한 정책·기준 충돌만 질문한다. 코드·문서로 답을 확인한 사실은 되묻지 않는다.

질문은 사용자 결정과 자료 충돌에 집중한다. 비용·데이터 의미·보안·외부 계약에 영향을 주는 기술 선택은 사용자 결정이며, 승인 범위 안의 쉽게 되돌릴 수 있는 구현 세부사항은 에이전트가 처리한다. 필요한 질문에는 배경과 선택의 영향을 설명하고, 근거가 있을 때 선택지와 추천을 제시한다. 앞 답에 의존하는 질문은 순서대로, 독립적인 질문은 소수로 묶는다. 확인한 사실과 명확한 동의는 재확인하지 않으며 모호함·충돌이 생긴 지점만 다시 묻는다.

초기 조사는 요구를 정리하기 위한 현재 동작·제약 파악이다. 구현 구조·손댈 파일·상세 테스트 설계는 PRD 확정 후 Plan 단계에서 다룬다. 질문이 없다고 가정을 숨기지 않는다. 결정할 사항이 없으면 조사 사실과 판단 근거를 PRD에 요약한다.

## 열린 질문의 능동적 해소

열린 질문을 발견하면 메인이 먼저 위 조사와 사용자 결정의 경계를 적용한다. 확인 가능한 사실은 조사로 해결하고, 승인 범위 안의 쉽게 되돌릴 수 있는 구현 선택은 근거를 밝히고 처리한다. 사용자 결정이 필요한 항목은 문서의 열린 질문 목록을 확인하라고 넘기지 않고 같은 대화에서 직접 질문한다. 질문에는 결정할 내용·배경·선택의 영향을 제시하고 근거가 있으면 추천안을 덧붙인다.

에이전트는 조사한 근거를 바탕으로 자신의 추천안을 적극적으로 제안한다. 가능한 대안과 장단점·위험을 설명하며 사용자가 선택하거나 다른 방안을 제시하도록 묻는다. 근거가 부족하면 부족한 점을 밝히며 선택지를 억지로 만들지 않는다. 추천은 사용자 답변과 구분해 기록하고, 사용자 결정이 필요한 정책을 동의 전에 확정하거나 구현하지 않는다.

질문이 적고 독립적이면 직접 묻는다. 목표·시나리오·제약이 전반적으로 모호하거나 결정들이 얽혀 구조적인 수집이 필요하면 메인이 [interview](../skills/interview/SKILL.md)를 읽고 수집 도구로 선택한다. 사용자에게 스킬 선택이나 별도 명령 입력을 요구하지 않는다. 확인한 답과 기존 project·slug·조사 문맥을 전달하고, 필요한 미결정만 질문한다.

start·prd에서 선택한 interview는 호출 흐름 안의 수집 모드다. 별도 씨앗 저장 승인이나 단계 명령을 추가하지 않고 답변을 현재 미승인 PRD에 반영한 뒤 원래 흐름으로 돌아간다. 독립 interview 직접 호출의 씨앗 저장 확인 경계는 유지한다. 이미 승인된 PRD·Plan은 덮어쓰지 않고 중요 결정의 변경 영향과 기존 재검토·재승인 경로를 안내한다.

PRD 승인 요청 전에 목표·범위·정책·수용 기준을 좌우하는 열린 질문을 대화에서 해소한다. 답변이 없으면 미결정과 영향을 명시하고 관련 승인·구현을 보류한다. 사용자가 중단하거나 답변을 미루면 반복 질문하지 않는다. 명시적으로 합의한 범위 제외·후속 과제는 남길 수 있지만 승인 요약에서 드러내며, 무응답을 동의나 에이전트의 정책 결정으로 바꾸지 않는다. status 같은 읽기 전용 조회는 이 질문·수집 흐름을 시작하지 않는다.

## 선택형 프로젝트 도입 조사

`init`의 환경·검증 명령 연결만으로 도입을 마칠 수 있다. 연결 뒤 프로젝트 지식 조사를 선택할 수 있으며, 생략해도 다른 스킬 사용을 제한하지 않는다. 도입 조사는 **프로젝트 전반**, 일반 작업 종료 점검은 **해당 변경과 관련된 범위만** 다룬다.

조사를 선택하면 실제 파일 목록과 기존 문서 색인부터 확인하고 코드·테스트·설정·`AGENTS.md`·`CLAUDE.md`를 읽는다. `project-context.py knowledge`의 domain 후보는 출발점이며 전반 조사 전체를 대신하지 않는다. 없는 자료를 가정하지 않고 접근 불가·자료 부재와 조사 한계를 표시한다. 결과는 다음처럼 구분한다.

- 확인한 기술 사실과 근거 경로·필요한 심볼/행.
- 기존 자료로 확인한 업무규칙·보안정책과 출처.
- 자료 간 충돌·근거 부족·미확인 가설과 확신의 한계.
- 새 정책·상충 정책의 우선순위 등 사람이 결정할 사항.
- 기존 문서를 유지할 이유 또는 보완·새 문서의 구체적인 제안.

조사로 해결할 수 있는 기술 사실을 질문으로 대신하지 않는다. 코드 동작만으로 제품·보안 정책을 확정하지 않는다. 문서 제안에는 대상 경로·수정 내용·이유·근거를 제시하고 사용자가 검토한 변경만 반영한다. **조사 선택은 문서 쓰기 승인이 아니다.** 기존 문서를 우선하며 적절한 출처가 없고 아래 durable knowledge 기준을 충족할 때만 새 문서를 제안한다. 자료가 없다는 이유로 문서를 일괄 생성하거나 `AGENTS.md`·`CLAUDE.md` 사용자 본문을 덮어쓰지 않는다. 반영 뒤 기존 출처를 연결하고 같은 내용을 복제하지 않는다.

## 재개

가능하면 `.tram/local/context/<slug>.md`에서 지난 조사 요약과 근거 경로·digest, 결정, 불확실성 및 읽은 지식을 확인한다. 이 파일은 재개를 돕는 메모이며 승인이나 검증 증거가 아니다. 메모가 없거나 저장할 수 없으면 대화·PRD·Plan과 코드를 기준으로 이어간다.

기록된 근거가 현재도 유효한지 관련 파일과 설정만 확인한다. 바뀐 근거는 다시 조사하고, 관련 없는 전체 프로젝트 조사를 반복하지 않는다. 경로에서 지식 후보를 못 찾았어도 기존 `docs/domain/README.md` 및 `docs/knowledge/README.md`를 가볍게 확인해 명시적인 연결을 찾을 수 있다.

## 지식 기록

일반 작업의 관련 정책 확인은 기존 knowledge 경로 매핑에 [하네스 관찰 검색](./runtime-contract.md#선택형-하네스-관찰-계약)을 보완할 수 있다. 요청 키워드·태그·적용 범위로 얻은 결과는 후보이며 실제 문서를 읽어 확인한다. 기존 매핑의 우선순위와 명시적 빈 설정을 존중하며 검색 도구로 이를 덮어쓰지 않는다. 검색 범위·잘림·출처·문서 digest·마지막 확인 시점·대체 관계를 확인하고, 결과가 없거나 metadata가 없으면 정책 없음이 아니라 미확인으로 설명한다. 문서의 확인 날짜는 현재 유효성의 보장이 아니다.

검색은 코드만으로 확정할 수 없는 결정의 출처를 찾는 보조 수단이다. 텍스트 의미의 충돌은 에이전트가 문서를 대조하며 제품·보안 정책의 확정은 사람에게 남긴다. 종료 시 해당 변경의 새 결정 후보·기존 설명 불일치를 점검하고 아래 지식 기록 경계를 적용한다. 문서를 자동 복제하거나 정책을 추정해 장기 규칙으로 승격하지 않는다. status는 이 검색·기록 흐름을 시작하지 않는다.

작업 결정을 기록할 때는 아래 경계를 적용한다.

| 내용 | 위치·처리 |
| --- | --- |
| 해당 slug에서만 유효한 선택, 미확인 가설, 진행 중 결론 | `.tram/local/tasks/<slug>.md`의 결정·제한·근거에 남긴다. 확정 사실처럼 승격하지 않는다. |
| 승인 범위 안에서 출처와 검증 상태까지 확인된 재사용 가능한 기술·프로젝트 사실 | 기존 목적별 프로젝트 문서를 우선한다. 적절한 문서가 없으면 `docs/knowledge/<slug>.md`와 색인에 기록을 제안하거나 남긴다. 일반 사실에는 별도 승인 게이트를 추가하지 않는다. |
| 서비스 domain의 정체·경계·관계 | 기존 `docs/domain/<slug>.md`와 domain 색인을 사용한다. 업무규칙·아키텍처를 domain 문서에 섞지 않는다. |
| 제품·사업·보안 정책, 요구 범위·우선순위 결정 | 사용자의 결정·승인 전에는 장기 규칙으로 기록하거나 구현하지 않는다. |

없는 `docs/knowledge/`나 색인은 필요가 실제로 생겼을 때만 최소 구성한다. 반복된다는 이유만으로 확인되지 않은 추정을 durable knowledge로 바꾸지 않는다.

기존 프로젝트 문서 중 각 사실의 역할과 범위가 맞는 문서를 먼저 사용한다. domain 문서에는 서비스 도메인의 정체·경계·관계만 기록한다. 업무규칙·아키텍처 등은 해당 목적의 기존 프로젝트 문서를 사용한다.

적절한 문서가 없고 작업으로 새 지식이 확정되면, 메인이 승인 범위를 확인한 뒤 문서 작업자에게만 `docs/knowledge/<slug>.md`의 최소 작성과 `docs/knowledge/README.md` 색인 연결을 배정한다. 서비스 domain의 결정은 기존 `/domain` 흐름과 색인에 기록한다. 미확인 가설은 확정 사실처럼 쓰지 않는다. PRD·Plan은 결정 스냅샷이므로 구현 결과에 맞춰 덮어쓰지 않는다.

`.tram/project.json`의 territories가 존재하면 기존 profile 우선순위와 `configure` 경로를 따른다. 명시적인 빈 배열은 사용자가 비운 설정으로 간주하고 TSV 항목으로 조용히 되돌리지 않는다. 누락·충돌 후보를 보고하고 의도된 제외인지 불확실하면 확인한다. legacy 설정만 있는 프로젝트는 기존 TSV 경로를 쓴다. domain 직접 호출은 전체 정체·경계·관계 인터뷰와 기존 사람 검토 게이트를 유지한다. start가 기존 확정 지식을 보완할 때 전체 인터뷰를 반복하지 않는다. retro는 별도 회고 역할을 유지한다.

승인 범위 안의 문서 보완은 구현의 일부로 마치고 최종 verify를 실행한다. 문서에서 새 업무정책이나 요구 범위가 필요하면 PRD 확정으로, 새 구현 설계가 필요하면 Plan 승인으로 돌아간다. 최종 verify 뒤 코드나 문서를 바꾸면 기존 증거가 유효하다고 가정하지 않는다.

기록 위치가 ignore되지 않거나 권한이 없으면 로컬 파일을 강제로 만들지 않는다. 작업자는 조사 요약과 제한을 반환하고 메인이 대화에 남겨 작업을 이어간다.

## 변경 관련 문서 점검과 보고

`impl`·`quick`은 최종 `verify` 이전에 변경한 동작과 연결되는 기존 업무규칙·아키텍처·운영 문서를 코드·테스트와 대조한다. 근거 있는 불일치는 이미 승인된 구현 범위와 문서 정책 안에서 보완한다. 승인된 보완에 반복 승인을 요구하지 않는다. 순수 문구 보완에 의미 없는 동작 테스트를 추가하지 않는다.

완료 보고에는 확인한 관련 문서·근거 경로와 보완 내용을 포함한다. 변경 불필요이면 기존 설명과 일치하거나 변경이 문서 설명에 영향을 주지 않는 구체적인 이유를 적는다. 관련 문서를 못 찾았으면 검색한 경로·색인 등 조사 범위와 확인 한계를 밝히며 자동 생성하지 않는다. 새 정책이나 승인 범위 밖 보완은 미해결 사항과 구체적인 제안으로 남긴다. PRD·Plan 본문은 승인 스냅샷으로 보존한다. 보완 후 최종 검증을 실행하며 검증 이후 코드·문서가 바뀌면 낡은 증거로 완료하지 않는다. `verify`는 이 점검 근거를 기존 지식 문서 대조에서 확인한다.

## 작업 공간 보호와 마무리

- 선택한 작업 경로가 기존 변경과 겹치는지 확인한다. 관련 없는 dirty·untracked 변경은 보존하고 계속한다. 겹침은 충돌 가능성의 단서이지 소유권 판정이나 자동 중단 근거가 아니다. 실제 충돌 부분만 사람에게 알린다.
- 현재 브랜치 재사용을 우선한다. 분리 작업이 명확히 필요하면 브랜치나 worktree 권장 이유를 설명한다. 확인 없는 stash·reset·checkout·stage·commit을 실행하지 않고 기존 전문 경로에서 이미 명시 승인된 계약을 유지한다.
- HEAD 없는 저장소에서 변경 전 기준선이 필요하면 대상 파일 경로를 명시해 `capture`한다. `compare`는 선택 파일의 존재·내용 digest·실행 비트 변화만 알려준다. 해시만으로 diff, 파일 소유권, 동시 편집 방지, 승인·검증 증거나 복원을 보장하지 않는다. 전체 저장소를 캡처하지 않는다.
- Git이 없으면 초기화하라고 강제하지 않는다. 현재 상태 비교와 로컬 기준선 저장이 제한되는 점을 보고하고 대화·코드 근거로 작업한다.
- 완료 보고는 구현 결과, 실제 검증과 미실행 항목, 지식 반영 여부와 이유를 밝힌다. commit·push·PR·현재 상태 유지는 권한과 사용자 요청에 따라 선택한다. 구현·검증 완료를 원격 통합 완료라고 표현하지 않는다.
