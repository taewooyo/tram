실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`와 [공통 실행 계약](../../context/runtime-contract.md)과 [작업 시작·재개의 사용자 경험](../../context/start-experience.md)을 먼저 읽는다. [프로젝트 경험 규칙](../../context/project-experience.md)도 읽는다. 변경 범위에 프로젝트 지식 문서가 포함되면 PRD·Plan과 현재 근거에 맞는지 검증한다. workspace digest는 작업 비교용일 뿐 검증 증거를 대체하지 않는다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


# /verify — 검증 일꾼 (판단만, 결정은 호출자)

[작업별 검증과 정책 관찰](../../context/start-experience.md#작업별-검증과-정책-관찰)에 따라 실제 실행 사실과 caller_reported 선언·사람 확인 대기·미실행을 구분한다. 선언된 scope를 실제 검사 범위의 증거로 사용하지 않는다. 관찰 경고는 기존 runtime 판정과 별도로 보고하고 필수 검사·fresh 독립 검토·예산·완료 조건을 유지한다. 관찰 record가 필요하면 메인이 저장하며 검증 작업자는 기존 검사와 판정만 반환한다.

## 런타임 증거 저장

### 모든 호출 경로의 검증 배정

impl·quick·coverage·perf-loop와 verify 직접 호출 모두 공통 사용자 경험 카드의 단일 오케스트레이션 절을 따른다. 메인이 상태·허용 범위·강도 이력을 확인하고 `transition --action verify --strength light|full`로 라운드를 연다. full·coverage는 full 필수이며 과거 full 작업을 light로 낮추지 않는다. perf light는 착수 시 확인한 저위험·동작 보존 테스트 근거를 `--reason`에 최소 인용한다. 이미 열린 라운드는 실제 강도·실행 상태를 확인해 이어가며 중복 배정하지 않는다.

사용자가 이 스킬을 직접 호출해 full 검증을 한 라운드 더 요청한 경우에만 이번 전이에 `--manual-full-continuation`을 추가한다. 이 신호는 full route·full 강도에서 기본 5회 상한과 정체 가드를 이번 호출에 한해 건너뛰며, 검증 한 라운드만 연다. 자동으로 다음 라운드를 시작하지 않는다. impl·start 등 상위 흐름이 호출한 verify에는 이 옵션을 붙이지 않는다. 호출 주체 표시는 runtime의 사용자 인증이 아니라 메인이 확인한 대화 경로다.

light는 메인 또는 구현 담당이 직접 실행할 수 있으며 별도 검증 작업자도 선택할 수 있다. full은 메인이 매 라운드 직접 생성한 fresh reviewer에게 배정한다. 작업자는 검사·판정 단계만 수행하며 다른 reviewer 생성·재위임·구현 파일 수정·사용자 질문·Task 갱신·runtime 전이를 하지 않는다.

메인은 project·slug·강도·검토 시작 `status.snapshot`·`task.round`·구현자 실행 참조·확정 프로필 명령과 검사 범위를 전달한다. 작업자는 `status`로 `verifying`과 `task.verification_strength` 및 전달 라운드를 확인하고 다르면 제한을 반환한다. 모든 task 명령에 `--project PATH --slug SLUG`를 붙여 필수 프로필 명령마다 `verify-run --command ID`를 실제 실행한다. 외부 종료 코드를 대신 등록하지 않는다.

full 담당은 공유 역할·루브릭의 기준 대조를 직접 수행하고 5축·근거·판정·실제 독립 실행 reference와 시작 snapshot/round를 메인에 반환한다. light는 검사 결과·판정·실행 reference와 시작 snapshot/round를 반환하며 리뷰 점수를 만들지 않는다. 메인은 full 합계·min-gate를 검산하고 [공통 실행 계약](../../context/runtime-contract.md)의 JSON 스키마로 대상 `.tram/local/`에 저장해 `review --file PATH`로 등록한다. 검토 실행 불가·빈 결과·JSON 거부·낡은 snapshot은 검증 오류이며 완료로 처리하지 않는다. 새 snapshot/round로 오래된 검토를 위장하지 않는다. complete/결함 분기와 결과 전이는 메인의 책임이다.

이 스킬은 검증의 **판단(judging)** 을 맡는다. 검사를 실행하고 판정(verdict)을 산출한다. 통과시킬지, 재시도할지, 위 단계로 올릴지 같은 **결정(deciding)** 은 호출자(`/impl`·`/quick`)의 몫이다. 이 스킬은 루프를 돌리거나 커밋하지 않는다.

> PR Checks·CI 같은 검증은 계속 자랄 수 있다. 그 확장은 이 스킬에만 넣어 `/impl`을 얇은 디스패처로 유지한다.

전달된 인자: 검증 대상(기능 slug 또는 “현재 변경”)과 강도 `light` 또는 `full`.

- 강도가 없으면 안전한 쪽인 `full`로 본다.

## 강도

### `light` — 테스트만

동작 보존 리팩터링, 순수 기계적 변경, 문서·설정, 영향 영역이 기존 테스트로 잘 덮인 좁은 버그 수정에 쓴다.

- 프로젝트의 관련 테스트를 실행하고 통과·실패 수치만 확인한다. `/quick`은 PRD·Plan 대신 사용자의 변경 요청을 검증 대상으로 삼는다.
- 순수 문구·주석·포매팅으로 실행 동작이 바뀌지 않아 관련 테스트가 없으면, 링크·문법 등 적용 가능한 검사를 실행하고 결과와 "테스트 해당 없음"의 이유를 기록한다. 검사 없이 통과했다고 보고하지 않는다.
- 적대적 기준 대조는 생략한다.
- 커버리지가 약하다고 판단되면 그 사실을 근거에 적고 `full`을 권고한다.

### `full` — 테스트 + 적대적 기준 대조

새 기능, 고위험 동작 변경, 보안·인증, 외부 입출력, 약한 커버리지 변경에 쓴다. 작고 저위험하며 기존·추가 테스트로 잘 덮인 동작 변경은 `/quick`에서 `light`로 검증할 수 있다.

- [코드 리뷰 루브릭](../../context/review-rubric.md)을 읽고, 아래 `[관점]`에 **카드 본문을 직접 포함**한다. 적용되는 프로젝트 컨벤션 카드와 최신 변경 diff·대상 경로도 전달한다.
- 모든 full 검증 경로에서 **메인이 매 라운드 fresh reviewer를 직접 생성**한다(`작업 식별자: reviewer_<라운드>`). 생성된 reviewer가 공유 역할 정의([`reviewer`](../../agents/reviewer.md))를 읽고 아래 계약의 검사·판정을 수행한다. adapter의 새 격리 실행으로 구현자의 대화·직전 리뷰 점수를 물려주지 않는다. 이전 reviewer나 구현 에이전트에 후속 작업으로 재채점을 맡기지 않는다. 이 스킬에는 적대적 검토 행동을 다시 적지 않고 아래 검토 계약만 전달한다.

```
먼저 <plugin-root>/agents/reviewer.md을 읽고 그 역할 정의를 따른다.

[기준] Plan 수용 기준과 PRD 시나리오:
<Plan·PRD 경로 또는 본문>

[대상] 구현 코드와 테스트:
<최신 diff·관련 경로·적용되는 프로젝트 컨벤션 카드>

[관점] 코드 리뷰 루브릭:
<plugin-root>/context/review-rubric.md 본문 — 5축·앵커·근거·min-gate·판정 규칙>

[객관 신호]
<프로젝트 관련 테스트 명령>

[판정 형식]
루브릭의 출력 형식을 따른다.
리뷰 점수 NN/100 · 5축 각각의 레벨과 구체 근거 · 0축 및 축 밖 블로킹 · 수용 기준 미충족
판정: 통과 | 구현결함 | 설계문제
필수 프로필 명령은 verify-run으로 직접 실행해 종료 코드·통과 N/M·강도 full·검토 한계와 실행 reference를 반환한다.
검토 시작 snapshot/round와 실제 독립 실행 reference를 함께 반환한다.
구현 파일 수정·사용자 질문·재위임·Task 기록·결과 전이는 하지 않는다.
```

- 메인은 reviewer가 반환한 5축 레벨(각 정수 0·1·2)의 합으로 점수를 재계산하고 0축 목록을 검산한다. 판정은 루브릭 매핑과 테스트 결과·수용 기준·축 밖 결함까지 확인해 보고한다. 점수나 레벨·근거·필수 검사 결과가 누락되거나 합계/판정이 모순되면 통과로 처리하지 않고 검증 오류를 보고한다. 이 검산은 새로운 품질 채점이 아니다.
- 향후 PR Checks·CI 결과도 이 단계의 신호로 합류시킨다.

## 관련 문서 대조

[변경 관련 문서 점검과 보고](../../context/project-experience.md#변경-관련-문서-점검과-보고)의 근거를 기존 지식 문서 대조에서 확인한다. light는 적용 가능한 검사와 보고 근거를 확인하며 full의 독립 기준 대조를 대신하지 않는다. 관련 업무규칙·아키텍처·운영 문서가 변경 동작과 일치하는지, 보완 또는 변경 불필요 이유가 구체적인지 확인한다. 자료 부재의 조사 범위·한계와 미결정 정책을 확인하고 PRD·Plan 스냅샷을 최신화하지 않는다. 보완 뒤 최신 코드·문서 기준으로 검증했는지 확인하며 낡은 증거를 통과로 처리하지 않는다.

## 판정

| 판정 | 의미 |
|---|---|
| **통과** | 테스트/검사 통과, full이면 수용 기준 충족·리뷰 ≥90·0축 없음·축 밖 블로킹 없음 |
| **구현결함** | 실패 또는 미충족이지만 구현을 고치면 해결 가능 |
| **설계문제** | 충족하려면 Plan 또는 PRD를 고쳐야 함 |

반드시 다음 형식으로만 보고한다.

```
## 판정: 통과 | 구현결함 | 설계문제
## 리뷰 점수 (full만)
NN/100 · 블로킹 0축 목록 · 축 밖 블로킹
## 축별 (full만)
5축 각각 레벨 0|1|2 및 파일:줄·테스트 출력 등 구체 근거
## 근거 / 미충족 항목
(구현결함·설계문제면 무엇이 / 왜 / 어떻게. 통과면 미충족 “없음”, 남은 1점 축은 개선 제안)
## 검사 결과
(테스트 통과 N/M · 강도 light|full · 커버리지 코멘트 한 줄)
```

## 수용 기준

- [ ] `light`는 테스트만 실행해 판정한다.
- [ ] `full`은 테스트와 독립 적대적 대조로 판정한다.
- [ ] 모든 호출 경로의 `full`은 메인이 직접 생성한 fresh reviewer에게 루브릭 본문을 전달하고 5축 레벨·근거·점수·블로킹을 산출한다. 합계와 min-gate를 검산한다.
- [ ] 판정은 통과·구현결함·설계문제 중 하나로 명확하다.
- [ ] 커버리지가 약하면 `light`에서도 그 사실과 `full` 권고를 기록한다.
- [ ] 루프·분기·커밋을 하지 않는다.

## 안전 규칙

- 없는 문제를 지어내지 않는다.
- 강도가 애매하면 `full`을 택한다.
- 서브에이전트가 빈 결과·오류를 반환하면 그대로 알린다.
- 테스트 실패·수용 기준 미충족·축 밖 블로킹은 점수가 높아도 통과시키지 않는다. `light`에는 리뷰 점수를 만들지 않는다.
