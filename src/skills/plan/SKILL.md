실행 주체는 [단일 오케스트레이션 계약](../../context/start-experience.md)의 직접 수행·위임 기준을 따른다. 아래 작업자 절차는 위임 시 적용하며 각 경로의 독립 검토·안전판은 유지한다.

새 승인 산출물의 읽기 구조는 [문서 규칙](../../context/doc-conventions.md)을, 승인 요약·재승인·문서 안내는 [공통 표시 정책](../../context/start-experience.md#요약문서-안내)을 따른다.

## 실행 경계

현재 스킬 파일의 `../..`를 plugin root로 해석하고 `<plugin-root>/adapter.md`, [공통 실행 계약](../../context/runtime-contract.md), [작업 시작·재개의 사용자 경험](../../context/start-experience.md), [프로젝트 경험](../../context/project-experience.md)을 먼저 읽는다. start에서 수집한 현재 동작·제약과 기존 지식 조사를 재사용하되, 승인된 PRD 이후의 재활용 코드 조사와 구현 설계는 이 단계에서 수행한다. 문서나 코드가 충돌하면 승인된 의도로 추정하지 말고 설계 선택이 필요한 내용만 보고한다. 대상 프로젝트는 사용자 지정 경로로 명시하며 plugin root와 혼동하지 않는다. 문서·명령의 상대 경로와 셸 cwd는 대상 프로젝트 기준이다. `<plugin-root>` 표기는 해석한 실제 경로로 치환하고 셸 경로는 인용한다. Native 도구·독립 검토 호출은 adapter를 따른다.


# /plan — PRD → Plan 단계 (② 설계)

## 런타임 기록

메인이 먼저 `status --project PATH --slug SLUG`로 `approvals_valid.prd`와 `effective_phase`를 확인한다. 문서의 확정 표식만으로 승인 완료를 판단하지 않는다. `plan_draft`에서 설계하고 사람에게 제출하기 전에 `transition --action submit-plan`을 실행한다. 이미 `plan_review`면 검토를 이어간다. 사람의 명시적 승인 뒤 `approve --scope plan --quote TEXT --session REF`로 최종 문서와 PRD 의존 digest를 저장한다. 모든 task 명령에 `--project PATH --slug SLUG`를 붙인다. 저장 성공 후 status로 유효성을 확인한다. start에서 진입한 흐름이면 전달 문맥을 유지하여 [impl](../impl/SKILL.md)을 읽고 실행한다. 직접 호출은 ②를 마치고 다음 행동을 안내한다. 승인 이전에는 구현하지 않는다.

[OS.md](../../OS.md) 개발 흐름의 **② Plan 단계**만 담당하는 스킬이다.
(배경·원칙은 OS.md를 따른다. 여기서는 그 단계를 실제로 어떻게 굴리는지만 적는다.)

입력은 **`/prd`가 확정한 PRD**(`docs/prd/<slug>.md`)다. 출력은 구현 설계 문서
(`docs/plan/<slug>.md`)다. 설계가 끝나면 **사람 검토 게이트에서 멈춘다.**

> 재활용 조사와 설계는 메인이 위험·범위·맥락 재구성 비용을 보고 직접 수행하거나 좁게 위임한다.
> 직접 수행 시에도 1차 스캔 → 불확실 영역 식별 → 설계 순서를 지키고, 불확실한 영역만 표적 조사한다.
> 위임 시 작업자는 재위임하지 않으며, 독립성·소유 범위·환경 한도에 따라 순차 또는 병렬로 배정한다.

전달된 인자: `$plan` 뒤의 사용자 메시지.
- 인자가 있으면 → 기능 설명/slug로 사용한다.
- 인자가 없으면 → start에서 전달받은 project·slug·요청·기록과 현재 대화의 문맥을 먼저 재사용한다. 확인할 수 없는 사용자 의도만 질문한다.

이 스킬의 범위는 **② Plan(설계)까지**다. ③ 구현은 게이트 통과 후 별도 스킬에서 한다.

---

## 진행 순서

### [준비] slug 확인 + PRD 확정 상태 확인

전달 문맥과 기록에서 slug를 확인하고, `exec_command`로 PRD 파일과 그 안의 상태 표식을 확인한다. `> 상태: 확정`은 문서 표식이며 runtime의 `approvals_valid.prd`가 유효해야 설계한다.

```
docs/prd/<slug>.md     # 입력 (있어야 함)
docs/plan/<slug>.md    # 출력
```

- **PRD가 없거나 `상태: 확정`이 없으면** → "먼저 `/prd`로 PRD를 정제·검토하고 사람 확정까지 마치세요"라고 안내하고 **멈춘다.** 수집 씨앗·검토 대기·상태 없는 기존 문서는 확정본으로 취급하지 않는다.
- **`상태: 확정`이면** → 그 PRD를 `exec_command`로 읽어 본문을 확보하고 1단계로 간다.

---

### 1단계: 1차 스캔 → 메인 갭 식별

메인이 승인 PRD에서 필요한 능력을 뽑고 `rg`·`rg --files`로 1차 검색·근거 정리를 수행한다. 넓은 코드 영역이나 독립적인 검색 묶음이 있어 분리 이점이 있을 때만 조사자를 배정하며, 결과를 메인이 통합한다.

1. PRD에서 **이 기능에 필요한 능력**을 항목으로 뽑는다. (예: "로그 파싱", "날짜 비교", "표 출력")
2. 각 능력마다 `exec_command`의 `rg`·`rg --files`로 **빠르게 1차 검색**한다. (관련 키워드·심볼·파일명)
3. 메인은 파일·심볼·재사용 근거와 불확실성을 세 갈래로 분류한다. 위임했다면 반환 근거와 연결한다:

| 분류 | 의미 | 다음 처리 |
|------|------|-----------|
| ✅ 찾음 | 재활용할 코드를 명확히 찾음 | 더 안 판다 (확정) |
| ❓ 불확실 | 있는 것 같은데 1차 검색으론 확신 못 함 | 2단계에서 깊게 조사 |
| ⬜ 못찾음 | 1차 검색에 안 잡힘 | 2단계에서 한 번 더 확인 (없으면 직접 구현) |

> 핵심: **확실한 곳(✅)엔 시간을 안 쓰고, 애매한 곳(❓⬜)만 다음 단계로 넘긴다.**
>
> **벤더 제외:** 1차 스캔·환경 확인 시 vendored/의존성 디렉토리(`.venv`·`node_modules`·`site-packages` 등)는 제외한다. "재활용 코드 N건"·"`.py` 0건" 같은 스캔 수치는 제외 후로만 세고, Plan에 **고정 단언으로 박지 않는다**(나중에 뒤집힌다).

---

### 1.5단계: 작업자 스키마·footprint 조사

> 왜 필요: 1단계는 **"뭘 재활용할까"(코드)** 에 초점이라, **"비슷한 걸 만들려면 어디를 다 채워야 하나"** 를
> 놓치기 쉽다. 한 기능이 **코드 + 데이터(DB/스키마) + seed/마이그레이션 + i18n/설정** 에 걸쳐 있을 때,
> 누락분이 설계·구현 중에 하나씩 발견되면 **라운드·토큰이 폭증**한다. 앞에서 한 번에 잡는다.
>
> (이 기법은 **레포에 무관**하다. 아래는 특정 테이블·경로를 가정하지 않고, 이번 레포에서 직접 찾아낸다.)

**트리거**: 이번 변경이 **"데이터로 정의되는 산출물을 새로 추가/복제"** 하는가?
(이미 **유사물(analogue)이 존재**하는 추가형 작업 — 예: 같은 종류의 항목/타입/엔트리를 하나 더 만드는 것)
- **아니오**(순수 코드 로직 변경·리팩터링·버그픽스) → 이 단계 건너뛴다.
- **예** → 메인이 footprint를 직접 역추적하거나, 범위가 넓고 독립적인 조사면 초기/좁은 조사자에게 배정해 반환 체크리스트를 통합한다.

1. **기준 유사물(analogue) 선택** — 만들려는 것과 가장 비슷한 **기존 것 하나**를 고른다.
   그것의 **고유 식별자**(id·code·이름·키 등 레포에서 그 항목을 가리키는 문자열)를 확보한다.
2. **그 식별자로 레포 전체를 역추적** — "이 유사물을 **존재하게 만드는 모든 것**이 어디에 있나?"
   ```bash
   rg -n --hidden -g '!.git/**' -g '!.venv/**' -g '!**/node_modules/**' -g '!**/site-packages/**' -F -- "<analogue 식별자>" .   # 코드뿐 아니라 데이터·시드·마이그레이션·설정·i18n 디렉토리까지 포함
   ```
   걸려 나온 **파일·테이블·행·등록 지점**이 곧 "내 새 항목이 똑같이 채워야 할 빈칸"이다.
   (식별자가 여러 형태면 — 숫자 id·문자 code·표시명 — 각각 검색해 합친다.)
3. **footprint 체크리스트**로 정리 — 각 항목: `<어디(파일/테이블/심볼)> — 무엇을 추가, 의존(순서·FK 등), 미정값`.
   불확실한 항목(❓)은 메인이 2단계 표적 조사로 배정한다.

> 한 줄 요령: **"기존 유사물 하나를 식별자로 끝까지 검색하면, 그게 곧 내가 채울 빈칸 목록이다."**
> 어떤 테이블·파일이 관련되는지는 **레포가 답을 준다** — 외워둔 목록이 아니라 이번 검색 결과를 쓴다.

---

### 2단계: 불확실한 부분만 표적 조사

**갭(❓·⬜)이 있으면**, 먼저 메인이 표적 검색으로 해소할 수 있는지 판단한다. 근거 수집이 넓거나 서로 독립적인 추가 조사에만 필요한 조사자를 배정한다. 작업자는 해당 부분만 조사하고 재위임하지 않는다. 독립적인 영역만 환경 한도 안에서 병렬 수행하고 선행 결과가 필요하거나 소유 범위가 겹치면 순차 수행한다. 확실한 영역은 중복 재조사하지 않는다.

- 도구: adapter의 독립 에이전트 실행
- 작업 식별자: `explore_<능력 이름>` (도구가 허용하는 영문 소문자·숫자·밑줄로 구성)
- 작업 목적: `"재활용 조사: <능력 이름>"`
- 전달 본문 (항목마다 채워서):

```
이 저장소에서 "<능력 이름>"에 재활용할 수 있는 기존 코드가 있는지 조사하라.
넓게 읽지 말고, 아래 단서로 표적 검색해 관련된 파일만 발췌해서 확인하라.
추가 서브에이전트는 띄우지 마라. 배정과 결과 통합은 메인이 한다.

검색 단서(키워드/심볼): <1단계에서 뽑은 키워드들>

다음만 간결히 보고하라:
- 찾음: <파일경로> — 무엇이고 어떻게 재활용하나
- 못 찾음: "없음 — 직접 구현 필요"
없는 걸 지어내지 마라. 표적 검색 결과만 보고하라.
```

- **갭이 0개면 이 단계를 통째로 건너뛴다.** (작은 레포·재활용 거리가 없을 때 비용 낭비 방지)
- 각 에이전트가 돌려준 결과를 모아, 1단계의 ✅ 찾음 + **1.5단계의 footprint 체크리스트**와 합쳐
  **"재활용 지도 + footprint 지도"** 를 완성한다.
  (재활용: 파일·사용법 / 직접 구현 / **채울 데이터·스키마: 테이블·파일·의존·미정값**)

> 조사 범위는 확인되지 않은 갭으로 제한하고 실행 순서는 의존 관계와 환경 한도에 맞춘다.

---

### 3단계: Plan 설계

재활용 지도가 확정되면 메인이 지도를 바탕으로 설계한다. 범위가 넓거나 독립 설계 초안이 실제 이점이 있을 때만 adapter의 독립 에이전트에 맡긴다. 위임하더라도 **재활용 조사는 이미 끝났으니, 지도를 신뢰하고 설계만** 하게 한다(코드를 다시 뒤지지 않게).

- 작업 식별자: `plan_designer`
- 작업 목적: `"구현 Plan 설계"`
- 전달 본문:

```
당신은 구현 Plan 설계자다. 아래 PRD와 "재활용 지도"를 바탕으로 구현을 설계하라.
재활용 조사는 이미 끝났다. 아래 지도를 신뢰하고 설계에 집중하라(코드를 새로 뒤지지 마라).

[중요] 지도에서 "재활용 가능"으로 표시된 것은 새로 만들지 말고 그대로 활용/확장하라.
(OS.md 원칙 2: 재활용 우선)

PRD (확정본):
<[준비]에서 읽은 PRD 본문>

재활용 지도 (1·2단계 조사 결과):
<능력별: 재활용 가능(파일·사용법) / 직접 구현 필요>

footprint 지도 (1.5단계 — 채울 데이터/스키마 체크리스트, 있으면):
<테이블/파일/심볼 — 무엇을 추가, 의존(FK·적용순서), 미정값. 없으면 "코드 변경만, 스키마 footprint 없음">

다음 형식의 마크다운으로만 답하라:
# Plan — <기능 이름>
## 재활용할 기존 코드 (지도 기반: 파일/스킬과 어떻게 쓸지)
## 직접 구현이 필요한 부분 (지도에서 "없음"으로 확인된 것)
## 손댈 파일 (신규/수정)
## 채울 데이터·스키마 (footprint 지도 기반: 테이블·seed·마이그레이션·i18n·설정 — 의존/적용순서 포함. footprint 없으면 "해당 없음")
## 구현 단계 (순서대로)
## 테스트 전략 (단위/통합 — OS.md 원칙 3, 필수)
## 위험 요소 / 롤백

단, "손댈 파일" 트리와 "구현 단계"는 반드시 **동일한 파일명·경로 체계**를 써라(트리가 정본). 한쪽만 고쳐 두 체계가 섞이지 않게 하라.
```

직접 작성 또는 위임한 초안을 메인이 검토해 `docs/plan/<slug>.md`에 저장하고, 실제 위임 실행 참조가 있으면 이를 기록한다. 수정은 범위에 따라 직접 하거나 좁게 배정한다. 메인은 결과 통합·사람 게이트·최종 승인 상태 저장과 runtime 기록을 맡는다.

### 복잡한 구현의 실행 정합성

단계가 많거나 여러 파일 소유자가 함께 작업하거나 공유 자원·코드 생성·산출물 재생성이 있는 경우에만 Plan에 실행 그래프 표를 추가한다. 단순하고 순차적인 작업은 현재의 간결한 순서형 단계를 유지한다. 복잡 표의 각 행은 `ID`, 선행 `depends`, 소유 파일, 공유 자원(없으면 없음), 생성·재생성 명령(없으면 없음), 생성 뒤 확인할 검사와 완료 증거를 담는다.

사용자에게 Plan을 제출하기 전에 메인이 각 의존 ID가 존재하는지, 의존성에 순환이 없는지, 겹치는 파일·공유 자원이 병렬 처리로 충돌하지 않는지, 생성 산출물마다 변경 후 검사 단계가 있는지 대조한다. 의존성은 실제 병렬/순차 배정 기준을 드러내며 새 scheduler나 기계 실행 가능한 상태 모델을 만들지 않는다. 충돌이나 재생성 누락은 제출 전에 Plan을 정합화한다.

### 검토 게이트 — ★반드시 멈춤★

Plan을 만들었으면 **요약해서 사람에게 보고하고 STOP 한다.**

```
✅ ② Plan 작성 완료 → docs/plan/<slug>.md

[재활용 조사 요약]
- 재활용: ... (찾은 것)
- 직접 구현: ... (못 찾아 새로 만들 것)
- 표적 조사한 항목: N개 · 실제 순차/병렬 배정 (갭이 없었으면 "1차 스캔으로 충분, 표적 조사 생략")

[footprint 요약] (스키마/데이터 추가가 있을 때만)
- 채울 테이블·파일: ... (기준 유사물 <id/code> 분해 결과)
- 미정값: ... (단가·아이콘·버전 등 사람 확인 필요)

[Plan 요약]
- 구현 접근: ...
- 손댈 파일: ...
- 테스트·검증 방법: ...
- 위험: ...

여기는 검토 게이트입니다. Plan을 확인해 주세요.
- ❓ 이 "재활용 목록"에 빠진 게 있나요? (당신이 아는 기존 코드가 있으면 알려주세요)
- ❓ "채울 데이터·스키마(footprint)"에 빠진 테이블/시드/설정이 있나요? (도메인 지식으로 메워주세요)
- 수정이 필요하면 어디를 고칠지 알려주세요(다시 설계합니다).
- 승인하시면 ③ 구현 단계로 넘어갑니다.
```

**이 게이트를 넘어 임의로 구현(코드 작성)으로 진행하지 않는다.** (OS.md 원칙 1 — 가장 중요한 안전장치)
사용자가 명시적으로 "승인", "구현 시작"이라고 말하기 전에는 ③으로 가지 않는다.

> 게이트에서 "빠진 재활용 있나요?"를 꼭 묻는 이유: 1차 스캔과 표적 조사도 완벽하진 않다.
> 코드를 잘 아는 사람이 누락을 메워주면, 정직한 1차 초안이 정확한 설계로 완성된다.

## 수용 기준 (이 스킬이 제대로 동작하는지 검증)

- [ ] PRD가 없거나 `상태: 확정`이 아니면 안내하고 멈춘다(씨앗·검토 대기를 확정본으로 취급하지 않는다).
- [ ] 메인이 PRD 기반으로 `rg`·`rg --files` 1차 스캔을 하고 찾음/불확실/못찾음을 나누며, 분리 실익이 있을 때만 독립 조사를 배정한다.
- [ ] 1.5단계: 데이터 산출물 추가형이면 **기준 유사물의 footprint(테이블·seed·설정)를 역추적**해 체크리스트화한다(순수 로직 변경이면 건너뜀).
- [ ] 갭이 있으면 메인이 필요한 표적 조사자를 직접 배정하고 독립성·환경 한도에 따라 순차 또는 병렬로 실행한다.
- [ ] 갭이 0개면 2단계를 건너뛴다.
- [ ] 3단계에서 확정된 재활용 지도를 바탕으로 직접 또는 실익에 맞게 위임해 설계한다.
- [ ] 복잡한 Plan에만 ID·depends·소유 파일·공유 자원·재생성·후속 검사 표를 두고, 제출 전에 cycle·누락·충돌·재생성 누락을 점검한다.
- [ ] `docs/plan/<slug>.md` 가 생성된다.
- [ ] 검토 게이트에서 멈추고, "빠진 재활용 있나요?"를 묻고, 승인 없이 구현으로 안 넘어간다.

## 안전 규칙

- **게이트를 넘지 않는다.** 사람의 승인 전에는 절대 ③ 구현으로 가지 않는다.
- **표적 조사는 갭이 있을 때만.** 비용(토큰·시간)을 의식해 무조건 띄우지 않는다.
- **footprint 스캔은 레포에 종속되지 않게.** 특정 테이블·경로를 가정하지 말고, **이번 레포에서 유사물을
  실제로 검색해 나온 것**만 체크리스트에 올린다(레포가 달라도 기법은 그대로 동작).
- **모든 산출물은 저장소 안에** 둔다(`docs/plan/`). (AGENTS.md 규칙 1)
- 서브에이전트가 빈 결과/오류를 돌려주면 그대로 알리고 멈춘다. 추측으로 채우지 않는다.
- 이 스킬은 **읽기·검색·문서 작성과 runtime 작업 기록**만 한다. 코드 파일을 수정하지 않는다(그건 ③ 구현의 몫).
